# 代理独立 API 地址实施记录

## 任务概述

本次打通了代理独立 API Base 的管理、展示和实际调用链路：

- 管理员在 `/admin/agents` 配置完整 API Base URL。
- 代理在 `/agent/system` 只读查看实际生效地址。
- 代理用户在 `/user/quickstart` 和密钥导入中获取所属代理地址。
- 独立 API 域名作为请求 `Host` 时，后端按 `agent.api_domain` 识别租户并校验 API Key 归属。
- 代理留空配置时，从数据库 `system_config.api_base_url` 动态回退平台共享地址。

## 核心逻辑

### 保存与回退

```text
管理端填写独立 URL
  -> 规范化为 scheme://host[:port]
  -> agent.quickstart_api_base_url = URL
  -> agent.api_domain = host

管理端清空
  -> agent.quickstart_api_base_url = NULL
  -> agent.api_domain = NULL
  -> 有效地址 = system_config.api_base_url
```

### 用户展示

`/api/user/profile/site-config` 继续保持原站点的 `site_scope` 与品牌字段，仅根据登录用户 `agent_id` 覆盖 `quickstart_api_base_url`。这使共享 API 请求和代理前台请求都能获得相同的代理 API Base，且不改变既有权限语义。

### 实际 API 调用

新域名经 nginx 保留原始 `Host` 反向代理至 `8085`。后端使用 `Host` 匹配 `agent.api_domain`，API Key 所属用户必须与目标代理一致。共享平台 API 仍保持原有的代理用户直连能力。

## 数据库

现有 `agent.quickstart_api_base_url` 和 `agent.api_domain` 已满足需求，本次：

- 没有新增或修改 ORM 字段。
- 没有修改初始化 SQL。
- 需在生产执行 `backend/sql/upgrade_agent_api_base_url_20260812.sql`。
- 该 SQL 不改表结构，只将“无独立 API 域名且值等于当前共享 API”的历史记录转为动态继承。
