# API 密钥累计费用溢出修复 Plan

## 用户原始需求

修复 `dangdangdang` 用户套餐额度耗尽后余额未扣费、请求显示计费异常的问题。

## 问题定位

- 生产库 `user_api_key.total_cost` 仍为 `DECIMAL(10,6)`，最大值为 `9999.999999`。
- 用户的 `codex` API Key 累计费用已经达到 `9999.999511`。
- 请求完成后的本地计费事务会同时扣余额、写消费记录并累计 API Key 费用。
- API Key 累计费用越界时 MySQL 抛出 `DataError 1264`，导致整个事务回滚，最终表现为余额未扣除和“本地计费或记账失败”。
- 当前 ORM 和部分初始化脚本使用 `DECIMAL(12,6)`，但生产历史表和根目录数据库快照仍存在较小精度，且没有对应升级脚本。

## 技术方案设计

1. 将 `UserApiKey.total_cost` 的 ORM 类型统一扩大为 `DECIMAL(20,6)`，为长期累计统计提供足够范围。
2. 同步修改三份初始化/快照 SQL 中 `user_api_key.total_cost` 的字段定义，避免新环境继续产生结构漂移。
3. 新增幂等升级脚本：仅当表和字段存在，且字段不是 DECIMAL、精度小于 20 或小数位不是 6 时执行 `ALTER TABLE ... MODIFY COLUMN`；已经具有更大整数容量且 scale 为 6 的字段不做缩小。
4. 新增结构一致性测试，校验 ORM、初始化 SQL 和升级脚本的目标精度。
5. 生产执行升级脚本后重启后端并验证：
   - 字段精度为 `20,6`；
   - 后端健康检查正常；
   - `dangdangdang` 的新请求能生成消费记录并扣减余额；
   - 不再新增 `total_cost` 越界异常。

## 风险与边界

- `ALTER TABLE` 可能短暂获取元数据锁；上线前检查表大小、长事务和元数据锁，并备份当前表结构。
- 升级脚本设置 15 秒锁等待上限。部署时先停止 8085 后端写入，执行失败则保持原表结构并立即恢复服务，不进行破坏性回滚。
- 脚本包含 MySQL CLI 的 `DELIMITER` 指令，必须使用项目部署流程中的 `mysql` 客户端执行。
- 本次只恢复后续请求正常计费，不自动补扣历史异常请求。历史未记账金额大于当前余额，需要单独确定欠费处理规则。
- 不改动套餐优先、余额兜底和混合扣费的业务逻辑。
