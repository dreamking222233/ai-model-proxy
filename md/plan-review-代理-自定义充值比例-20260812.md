## 1. 方案完整性

### 已覆盖充分的部分

- 兼容策略清晰：历史代理默认不开权限，关闭权限后回到全局用户比例。
- 财务上限思路合理：`custom_recharge_rate <= min(余额结算比例, 图片积分结算比例)` 可阻止直接充值分润为负。
- 请求 Schema 拆分方向正确：代理端不再复用管理端 `AgentUpdate`，可以缩小越权面。
- 套餐入口同时在公开配置、列表接口、下单接口和页面中限制，方向正确。
- 保留套餐原始开关，权限关闭后恢复原配置，可避免不可逆的配置覆盖。

### 必须补充的内容

1. **明确权威充值策略的类和方法签名。**

   Plan 在第 86、266 行已指出共享 API 域名绕过风险，但实施设计仍主要描述 `AgentSiteContext`。当前 `PaymentService.assert_recharge_enabled_for_site()` 只接收站点上下文，`/subscription-plans` 也只按该上下文判断；共享 API 直连时上下文可为 `platform`。

   v2 应定义类似 `AgentRechargePolicy` 的值对象，并明确 `resolve_user_recharge_policy(db, user)` 为服务端权威入口。该策略至少包含：

   - 代理是否存在且为 `active`；
   - 在线充值总开关；
   - 套餐原始开关与有效开关；
   - 自定义定价权限；
   - 余额、图片积分的有效用户比例；
   - 两类代理结算比例与动态上限。

   `create_recharge_order()`、`list_subscription_plans()` 和登录用户的 `/api/user/profile/site-config` 都应消费同一策略。域名上下文仅用于公开页展示、账号归属校验、来源快照和支付回跳。

2. **补充代理异常状态的失败规则。**

   `user.agent_id` 非空但代理不存在、已停用或配置非法时，必须失败关闭，不得回退成平台直营用户比例。该规则应有独立错误码和验收用例。

3. **明确开启权限时的存量比例校验。**

   Plan 只写了“修改比例时”校验权限和动态上限。管理员将 `custom_recharge_rate_enabled` 从 `0` 改为 `1` 时，也必须校验已保存比例是否仍在当前上限内；否则开权限后所有充值订单都会在下单时失败。

   同时要明确结算环境变量从 `7` 调低后的运维策略：发布前检查所有已开权限代理，超限则阻断发布或先关闭对应权限。

4. **明确配置切换对待支付订单的语义。**

   现有支付回调按订单快照入账，不会重新读取当前代理配置。因此：

   - 修改比例后，旧待支付按量订单仍会按旧比例入账；
   - 开启自定义定价权限后，之前创建的待支付套餐订单仍可能支付并开通套餐。

   v2 必须在“快照继续有效直至订单过期”与“切换时关闭待支付订单”中选定一种规则。若采用前者，应写入验收标准，避免将快照行为误判为限制绕过。

5. **补充推广返利的成本口径。**

   `PaymentService._apply_paid_order()` 在按量充值成功后调用 `PromotionService.apply_recharge_reward()`，而推广奖励按 `credited_usd` 或 `credited_image_credits` 的比例计算。自定义比例因此会同步改变推广奖励量。

   Plan 中“不会生成负分润”只校验了当前订单直接到账资产，没有包括推广奖励。v2 应明确推广奖励由平台承担还是纳入代理成本。即使确认为平台承担，也应将 `backend/app/services/promotion_service.py` 和对应回归测试列入影响范围。

6. **补充财务配置变更审计。**

   比例和定价权限会直接影响用户资产及代理现金。项目已有 `operation_log` 和 `LogService.create_operation_log()`，建议复用现有审计日志，记录操作人、代理 ID、权限/比例的前后值及操作来源。

## 2. 技术选型

### 合理的选择

- 在 `agent` 表保存代理级配置，与现有站点开关归属一致，无需引入新的配置系统。
- `DECIMAL(12,6)` 与现有结算比例、美元到账精度一致，适合财务计算。
- 在服务层进行动态上限校验，不把可变的结算比例写入数据库 `CHECK` 约束，选择合理。
- 继续复用支付订单的最终到账和分润快照，可保持支付回调幂等与历史数据稳定。

### 建议调整的技术点

1. **将策略解析和金额计算分层。**

   建议由 `AgentService` 返回经验证的策略对象，`PaymentService._calculate_amounts()` 只使用已解析的 `Decimal` 比例做纯计算。这样可避免列表接口、配置接口和下单接口各自实现一套条件。

2. **分离公开有效配置和可编辑原始配置。**

   Plan 第 182 行开始将公开配置与代理配置的返回字段合在一起。建议拆为：

   - 公开/用户端：只返回 `balance_recharge_rate`、`image_credit_recharge_rate`、`online_recharge_enabled` 和有效套餐开关；
   - 代理端鉴权接口：额外返回权限、原始比例、动态上限和套餐原始开关；
   - 管理端：返回权限、已保存比例和必要的有效状态。

   公开接口无需暴露关闭权限后保留的比例、`max_custom_recharge_rate` 或 `subscription_online_recharge_configured`。

3. **删除或严格定义模糊的 `recharge_rate` 字段。**

   平台余额与图片积分使用两个独立环境配置，未来可能不相等。前端应直接使用两个明确字段；若保留 `recharge_rate`，必须定义两者不相等时的返回语义。

4. **增加有效用户比例订单快照。**

   现有 `credited_*`、`agent_settlement_rate` 和 `agent_income_cny` 可保证正确入账，但不足以直接审计订单使用的用户比例。建议在 `payment_recharge_order` 增加 `user_recharge_rate` 或 `recharge_rate_snapshot DECIMAL(12,6)`，并在管理端/代理端订单明细返回。若决定不增字段，v2 也应明确“最终到账量为审计依据，比例仅由到账量/付款额推导”的取舍。

5. **保持全链路 `Decimal` 语义。**

   Schema、Service 和 ORM 使用 `Decimal`，精度统一量化到 6 位。前端显示可以转 `Number`，但提交时应避免二次四舍五入，并补充 `0.01`、`7`、超上限和 6 位小数边界测试。

## 3. 实施可行性

- `Agent` 已承载站点级在线充值和套餐开关。
- `PaymentService.create_recharge_order()` 在创建订单时完成资产与分润计算，改造点集中。
- 支付成功链路仅使用订单中的到账和分润快照，不需要重写回调幂等机制。
- 前端充值页的所有硬编码 `5` 已可定位，可收敛到两个计算属性。

## 4. 潜在风险

### 高风险

1. **共享 API 直连下的策略绕过或展示/下单不一致。**

   控制：所有登录用户支付决策仅按 `user.agent_id` 解析；请求域名不参与比例和购买权限决策。

2. **开权限后存量待支付套餐订单继续入账。**

   控制：先确定业务规则，再对创建时点、支付时点、配置切换时点编写测试。

3. **推广返利使实际资产成本超过直接订单结算成本。**

   控制：明确费用承担与上限公式口径，增加带推广关系的余额/图片积分支付回归。

4. **测试范围与支付链路风险不匹配。**

   控制：除计算单测外，必须覆盖权限更新、策略解析、共享 API 域名、套餐列表/下单、支付快照入账、平台用户回归与推广返利。

### 中风险

5. **已保存比例在结算配置变更后超限。**

   控制：保存、开权限、下单三处校验，并增加发布前数据检查。

6. **公开接口泄漏或混淆原始配置。**

   控制：拆分公开有效 DTO 和鉴权编辑 DTO，前端用户页只依赖有效字段。

7. **配置变更缺少可追溯记录。**

   控制：复用 `operation_log`，记录前后值及操作人。

8. **初始默认值 `5` 与运行时全局比例可能不一致。**

   控制：历史代理权限默认关闭；新建代理时由 Service 用当前全局用户比例显式初始化，开启权限前再校验动态上限。

## 建议的测试矩阵

- 平台用户：余额、图片积分、套餐行为不变。
- 代理用户未开权限：两类按量充值使用全局比例，套餐按原开关。
- 代理用户已开权限：余额/图片积分分别按自定义比例入账，套餐列表为空且下单被拒绝。
- 共享 API 域名：登录代理用户的显示策略与下单策略一致。
- 权限边界：代理不可修改授权字段，未授权时修改比例失败，管理员开启超限存量比例失败。
- 数值边界：`0.01`、动态上限、超上限、0、负数、超 6 位小数和非数值。
- 状态边界：代理不存在/停用、在线充值总开关关闭、结算配置低于存量自定义比例。
- 时序边界：创建订单后修改比例/权限/套餐开关，验证待支付订单按选定业务规则处理。
- 财务回归：订单比例、到账量、结算比例、代理分润、现金流水和重复回调幂等。
- 推广回归：带推广关系的余额/图片积分充值，验证奖励量和成本口径。
- 数据库：升级 SQL 连续执行两次、新库初始化字段一致、历史代理默认权限关闭。

## 最终建议

保留现有数据模型、动态上限、订单快照和前端改造的主体方案。先按“v2 必改清单”修订 Plan，重点锁定用户归属策略、待支付订单语义、推广成本和审计/测试。v2 完成这些修订后，方案可进入实施阶段。
