# Plan 可行性评审：模型渠道分组与 API Key 分组

## 结论

方案可行，允许进入实施阶段。业务规则、兼容策略、路由边界和计费公式能够映射到现有 FastAPI + SQLAlchemy 架构；实施必须以 Plan v2 的 Tasks 为准。

## 必须修订并已纳入 v2

1. 前端实际日志文件为 `RequestLog.vue`、`AgentRequestLog.vue`，已修正文件清单。
2. 数据迁移必须先按 `UnifiedModel.model_series` 创建默认组，再回填历史映射，最后切换唯一约束 `(unified_model_id, group_id, channel_id)`，避免旧数据丢失或冲突。
3. 历史 API Key 路由字段为空时必须归一化为通用模式；专用 Key 只能保存单一系列和单一分组。
4. 通用 Key 的模型列表必须逐系列使用默认组并过滤实际有效映射，不能返回其他分组同名模型。
5. 分组解析必须覆盖 Chat、Responses HTTP/WebSocket、Anthropic Messages/count_tokens、原生透传、图片和视频；WebSocket 会话与异步视频任务要冻结分组上下文。
6. 分组倍率只进入 Token 文本计费。图片、视频、按请求和套餐官方额度保持旧逻辑；`system_config.price_multiplier=1` 为部署前提，不与新分组倍率重复相乘。
7. 日志、消费记录和视频任务保存分组 ID、名称、倍率快照，不能依赖当前分组表反查历史。

## 风险与实施控制

- 分组停用或组内无渠道时返回专属错误，不跨组回退。
- 默认组切换需保证同系列最多一个启用默认组，并校验旧 Key 的可用性。
- 预检、成功扣费和失败日志复用同一冻结计费上下文，防止倍率即时修改造成单次请求前后不一致。
- 每个阶段完成后运行针对性测试和静态检查，最后再进行全量构建与文档归档。
