# 代理开放接口与接入管理计划（v2）

方案版本：v2；已根据 `plan-review-代理开放接口-20261017.md` 最终评审通过，进入编码。

## 用户原始需求

深入了解项目及文档，扩展代理端开放接口：代理可生成 API Key、配置权限，并查看和一键复制 Markdown 接入文档；外部 AI 桌面工作台可通过本系统注册、登录、给用户充值、查询请求详情和充值记录。已登录用户还可创建模型调用 API Key，并按 `/user/api-keys` 选择模型系列和分组。

注册/登录字段沿用当前页面；登录增加用户美元余额。在线充值接受支付宝或微信，按 `a`–`g` 选择每人民币对应的美元数（1–7），默认 `e=5`；代理可选择自己的用户到账比例，代理结算比例仍按系统既有规则（当前常见 1:7）计算，结算成本外的部分记入代理分润。接口需返回支付宝链接或微信 Native 二维码凭据，并支持最长 120 秒同步等候付款结果。请求详情和充值记录参考 `/agent/logs`、`/agent/payments`。

## v2 评估后固定的业务契约

0. **分组字段契约**：`group_mode` 仅允许 `unified`、`special`。`unified` 不传 `group_model_series`/`group_id`，服务端使用当前启用的默认统一分组；`special` 必须同时传模型系列和分组 ID，并重新校验分组启用状态与系列归属。选项接口返回 `ModelGroupService.list_options()` 原结构：`series`/`model_series`（每个模型系列含 `value`、`label`、`default_group_id`、`groups`）、`groups`、`groups_by_series`；页面以 `special` 选择系列和分组，`unified` 使用运行时默认分组。创建仍按服务端校验当前分组状态和系列归属。
1. **可信租户**：开放 API 租户只由已验证 API Key 数据库行中的 `agent_id` 决定。开放 API 不用 Host、`X-Site-Host`、Origin 或 Referer 推导租户/支付回跳，也不接受请求体中的代理 ID。代理必须 active；注册还须开启 `allow_self_register`。登录在校验密码后、签发 JWT 前校验 `role=user` 且 `user.agent_id == key.agent_id`。充值、等待及模型 Key 创建再验证 Key、用户和订单/Key 归属一致。代理 Key 管理的列表、scope 更新和撤销均从管理员 principal 强制注入 agent_id，并以 `key_id AND agent_id` 锁定目标行。
2. **站点上下文**：由可信 `agent_id` 在服务端读取 Agent 并创建 API 专用 `AgentSiteContext`。支付回跳只使用该 Agent 已配置的 `frontend_domain`；缺少域名时用其站点配置确定性失败，绝不采用调用方来源头。JWT 在开放 API 使用只验证令牌、撤销状态、用户状态的专用依赖；通用浏览器依赖仍保留现有站点匹配。注册验证码按 agent_id + email + register purpose 隔离并一次性消费；不接受 password_reset purpose。
3. **比例与分润**：开放接口只支持美元余额充值。固定映射 `a=1`、`b=2`、`c=3`、`d=4`、`e=5`、`f=6`、`g=7`，表示每 1 CNY 到账的 USD 数量；缺省为 e。结算比例同单位解释（每 CNY 可结算的 USD），例如 100 CNY、用户比例 a、结算比例 7 时到账 100 USD、成本为 100/7=14.29 CNY、代理收入为 85.71 CNY。非 e 单笔覆盖仅在管理员已开启该代理 `custom_recharge_rate_enabled` 时可用，且有效 Decimal 比例不能超过当时余额结算比例。e=5 也须满足当前结算上限。人民币金额先按 0.01 元、到账美元按 0.000001 美元、代理成本/利润按 0.01 元采用 HALF_UP 舍入。有效比例同时传入 `PaymentService` 的到账和分润计算，订单保存 `user_recharge_rate` 及比例代码快照；幂等重试必须使用已保存的订单比例快照，不重新读取比例配置；结算比例、到账额、分润仍由原服务生成订单快照并由原支付成功入账逻辑处理。该单笔权限不改代理全局 `custom_recharge_rate`，也不替换现有网页充值统一比例。
4. **创建与等待**：单个 HTTP 请求无法先返回付款凭据再等待付款，故开放流程是先 `POST` 创建订单、展示凭据，再 `POST /{order_no}/wait` 同步等候最多 120 秒。创建响应不等待付款；等待成功只认渠道查单或签名回调确认的 paid。HTTP 等候超时不是支付失败。
5. **订单超时与关闭**：等待截止前预留有界的渠道关单预算；在截止后才到达的请求不再发起外部请求。渠道确认关闭后才将本地订单改为 closed。关闭渠道超时或状态不确定时，响应为 `wait_result=wait_timeout`、`order_status=pending`、`close_result=uncertain`，不能把 `close_uncertain` 伪装成数据库订单状态；回调和后续查单仍可恢复。若 closed 订单之后收到渠道签名有效且金额必须存在、匹配的成功通知/查单结果，允许锁内从 closed 升级为 paid 并按既有结算幂等账本入账。支付宝渠道下单仍设 30 分钟有效期；微信 Native 增加同样的 `time_expire`；120 秒关单是早期取消策略，不能替代真实 TTL。支付渠道确认的成功交易优先于本地过期时钟；缺少支付金额、金额不符或订单号/商户信息不符均拒绝入账。
6. **等待资源**：等待路由为 async，单调时钟控制硬截止，`asyncio.sleep` 不占工作线程。该路由及其 Key/JWT principal 不注入 request-scoped `get_db`：鉴权分别在独立 Session 读取必要标量字段后关闭；每轮状态读写在线程内新建独立短 Session，不跨线程传递 Session 或 ORM 对象，提交/关闭后才睡眠或访问渠道。并发槽立即获取，满载立即 429，不排队后延误截止时间。120 秒单调时钟从路由接收开始；预留至少 10 秒关单/响应预算，查单只有在剩余时间大于单次硬超时 + 关单预算时启动，关单时间硬限小于剩余预算；到截止前停止轮询。同步 SQLAlchemy 和支付 SDK 调用须用有界线程池执行；支付宝 SDK 与微信 HTTP 都必须设置可验证的单次网络超时，不得依赖 `asyncio.wait_for` 伪造线程取消；等待超时不能终止工作线程，因此渠道 transport 本身必须通过真实连接/读取超时确保线程在硬截止前结束；若 SDK 不可配置，则更换为可控的 HTTP transport。使用有上限的等待并发（单进程 32，并明确总容量为 worker 数乘该值）、间隔轮询及 Key/IP/用户频率限制；受控支付线程池配置有限 worker 和队列，不允许长尾任务无限堆积。入口层等待超时必须高于 120 秒（建议至少 130 秒）；部署与接入文档注明 Nginx/Gateway/Uvicorn worker 配置，客户端也需配置更长超时。若无法令任一通道单次请求在截止前确定返回，则本次等待明确作为“尽力等待”，不能承诺渠道操作本身一定在 120 秒完成。
7. **充值幂等**：创建必须有 `Idempotency-Key`（8–128 个可见 ASCII 字符）。以 Key + 用户 + 幂等值 SHA-256 建唯一索引；reservation 状态仅为 `reserved/provisioning/ready/retryable_failed`。reservation 保存请求指纹、规范化请求参数、有效用户比例代码和值、结算比例值、预留订单号、租约截止时间和尝试次数；lease 固定 10 分钟，完成记录保留 30 天。请求指纹使用规范化后的 2 位 CNY、支付渠道、比例代码、Key ID、用户 ID、代理 ID 的 canonical JSON + SHA-256。reservation 先短事务持久化；预留订单号同时用于创建本地订单，随后才调用支付渠道。相同参数复用原单：`ready` 时按订单真实状态响应，`pending` 返回现存凭据，`paid` 返回已支付状态，`closed/failed` 返回状态并要求新的幂等键，不得返回过期凭据；有效租约内的 `provisioning` 返回含 Retry-After 的 409；租约过期时先按预留订单号查询渠道/本地订单，再安全恢复。支付宝查询超时也必须查单恢复，NOT_FOUND 才可同号重新生成本地支付链接；微信查单成功且 local code_url 已保存时复用，远端 pending 但本地二维码丢失时，必须确认关掉旧单后才更新 reservation 的预留号并创建新单；关闭状态不确定时不得换号。paid/金额不符等状态遵守订单快照和账务规则。明确失败才进入 retryable_failed。相同值不同参数返回 409。事务竞态由唯一约束捕获并重新读取 reservation。金额仅人民币 `1.00`–`10000.00`，最多两位小数；每用户/Key 执行限流。reservation 字段在 30 天清理后重用相同幂等值视为新请求；订单、reservation 与渠道创建的崩溃窗口必须有故障注入测试验证。
8. **Key 生命周期**：独立表每代理最多 20 个 active Key；随机 256-bit、`agk_` 前缀；只保存 SHA-256、前缀、名称、固定 scope 列表和元数据。默认有效期 90 天，可选 1–365 天；无过期 Key 不开放。创建响应仅显示一次明文，列表和日志不返回明文，响应禁缓存。支持 scope 更新、撤销；创建新 Key 后由代理迁移再撤销旧 Key 即为轮换。代理停用、Key 到期、撤销均立即拒绝；管理动作写操作审计，不含密钥。丢失只能重新创建/轮换。
9. **等待接口身份**：充值创建及等待需要 `X-Agent-API-Key`、对应充值 scope 和用户 `Authorization: Bearer <JWT>`。JWT 必须是 Key 所属代理的终端用户。等待还必须按 `order_no + user_id + agent_id` 定位订单，其他租户与不存在订单返回同一 404。
10. **查询范围**：请求详情按 `request_id AND agent_id` 精确查询，关联消费记录同时加 agent/user 范围，再使用代理可见 DTO 和错误脱敏。充值列表服务强制传入 Key principal 的非空 `agent_id`，仅接受 page、page_size、user_id、status、payment_channel、recharge_type、日期筛选白名单；任何请求字段都不能覆盖租户范围。支付凭据、支付通知原文不进入 DTO。
11. **响应与错误**：保持全局 `{code,message,data}`。成功和等待返回稳定开放 DTO；等待 `wait_result` 为 `paid`、`wait_timeout`、`closed`、`failed` 之一，`close_result` 为 `not_attempted`、`confirmed`、`uncertain` 之一；`wait_timeout` 以 200 返回业务状态（另含真实 `order_status`），不伪装成成功或失败。使用现有 ServiceException/全局异常转换，文档列 400/401/403/404/409/429/500/503 及 `error_code`。开放代理 Key、模型调用 Key 等所有明文 Key 创建响应，以及注册/登录/等待响应均设 `Cache-Control: no-store`。

## API 契约

统一前缀 `/api/agent/open/v1`，密钥头 `X-Agent-API-Key`；需用户身份的端点同时传 Bearer JWT。

| 方法 | 路径 | Scope | 请求 | 返回 data 核心字段 |
|---|---|---|---|---|
| POST | `/auth/email-code` | `auth.register` | `{email}`；固定 register purpose | `{message}` |
| POST | `/auth/register` | `auth.register` | `{username,email,password,email_code,invite_code?}` | `{token,user}` |
| POST | `/auth/login` | `auth.login` | `{username,password}` | `{token,is_first_login,user,balance}`；balance 为 USD，不含图片余额 |
| POST | `/users/recharge-orders` | `user.recharge` + 用户 JWT | `{amount_cny,payment_channel,recharge_rate_code?}` + `Idempotency-Key` | `{order_no,status,amount_cny,credited_usd,user_recharge_rate,expired_at,payment_channel,pay_url? ,wechat_code_url?}` |
| POST | `/users/recharge-orders/{order_no}/wait` | `user.recharge` + 用户 JWT | 无 body | `{wait_result,close_result,order_status,order_no,paid_at?,balance?}`；等待 paid 后含 USD balance；订单状态只允许真实 `pending/paid/closed/failed` |
| GET | `/user/api-keys/group-options` | `user.api_key.create` + 用户 JWT | 无 query | `ModelGroupService.list_options()` 的启用分组选项：`series`/`model_series`、`groups`、`groups_by_series` |
| POST | `/user/api-keys` | `user.api_key.create` + 用户 JWT | `{name,group_mode,group_model_series?,group_id?,daily_limit_usd?}` | 复用模型调用 Key 创建响应 `{id,name,key,key_prefix,group_mode,group_model_series,group_id,...}`；完整 `sk-` 仅创建响应返回 |
| GET | `/agent/requests/{request_id}` | `agent.request_detail` | UUID 路径参数 | 单条代理脱敏日志 DTO |
| GET | `/agent/payments` | `agent.recharge_records` | 白名单分页/过滤 query | `{list,total,page,page_size}`，与代理充值记录订单字段一致 |

等待返回 `wait_result=paid|wait_timeout|closed|failed`，`close_result=not_attempted|confirmed|uncertain`；关闭不确定时订单保持 `pending`。

管理 API（只用代理管理员 JWT，不用开放 Key）：

- `GET /api/agent/open-api/keys`：列表元数据和当前 scopes。
- `POST /api/agent/open-api/keys`：`{name,scopes,expires_in_days?}`；校验 scope 白名单及数量，明文仅在创建时返回。
- `PUT /api/agent/open-api/keys/{id}/scopes`：替换 scope，撤去的权限立即生效。
- `DELETE /api/agent/open-api/keys/{id}`：撤销并审计。

Scope 白名单：`auth.register`（含绑定代理及 register purpose 的邮箱验证码）、`auth.login`、`user.recharge`、`user.api_key.create`（只创建归属 JWT 用户的模型调用 Key 并读取可选分组）、`agent.request_detail`、`agent.recharge_records`。禁止 scope 扩展或任意字符串。用户模型调用 API Key 是 `UserApiKey` 的 `sk-` Key；它不是 `AgentOpenApiKey`，不具备开放接口 scope。

## 风险与边界

- 支付渠道关单与付款同时发生时以渠道确认的成功为准；如果本地已 closed，签名有效/查单成功且金额一致仍允许依靠支付结算表幂等补入账。
- 共享 API 域名不会参与租户判断；实际发验证码和 CORS 仍须服务端现有邮件/CORS 配置允许。
- 开放 API 不开放图片积分、套餐购买、代理余额管理或提现。
- 120 秒等待依赖外部入口超时配置；代码在响应前硬截止，部署文档要求 Nginx/API Gateway 的 read timeout 至少 130 秒。Key 速率限制 Redis 不可用时按现有 AuthRateLimitService 的内存 fallback 执行。
