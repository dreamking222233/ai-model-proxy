## 一、用户原始需求

当前系统同时存在用户套餐和美元余额，正常计费顺序为“套餐当期额度优先，套餐不足后扣美元余额”。现需增加一类用于促销的赠送套餐额度：

1. 管理员在 `/admin/subscription` 的“套餐用户”区域，对当前仍有有效套餐的用户点击“赠送额外套餐”。
2. 赠送时可选择：
   - 固定赠送若干天，例如 10 天；
   - 跟随当前用户套餐到期日，例如当前套餐还有 21 天，则赠送额度在此期间保持有效。
3. 管理员设置每日赠送额度，统一按美元计量，例如 `$100/天`。
4. 赠送额度只能用于指定模型。管理员在 `/admin/models` 编辑模型时，可设置该模型是否为“赠送额度模型”。
5. 请求命中赠送额度模型时，计费优先级必须为：
   - 赠送额度；
   - 用户正常套餐额度；
   - 用户美元余额。
6. 请求未命中赠送额度模型时，保持原顺序：正常套餐额度 > 用户美元余额。
7. 必须重点防止以下回归：
   - 套餐当期额度已经用完，请求仍继续且不扣余额；
   - 用户余额已经用完，请求仍继续；
   - 用户仅剩少量余额时，请求成功但没有任何资产被扣减；
   - 并发、流式或记账异常导致上游已返回、系统却没有可追溯的扣费记录。
8. 套餐模板可选择“全部模型”或指定一个/多个模型系列，例如只覆盖 Grok 系列；指定系列套餐仍可配置每日美元额度（如 `$100/天`）或无限额度。
9. 指定多个系列时共享套餐的一份每日额度，不按系列复制额度；未选系列不消耗正常套餐，直接按适用的赠送额度和用户余额结算。
10. 套餐模板修改后不改变已开通套餐的系列范围，开通时必须保存系列快照。

## 四、当前系统真实逻辑分析

### 4.1 套餐数据模型与有效套餐选择

当前套餐主要使用：

- `user_subscription`：用户套餐快照，保存套餐起止时间、额度口径和值；
- `subscription_usage_cycle`：套餐每个额度周期的累计用量；
- `sys_user.subscription_type/subscription_expires_at`：仅为套餐状态缓存，真实套餐以 `user_subscription` 为准；
- `consumption_record`：每次请求的理论费用、余额前后值、正常套餐周期和额度用量快照。

`SubscriptionService.resolve_active_subscription(...)` 按用户查询 `start_time <= now <= end_time` 的有效套餐，并按 `end_time DESC, id DESC` 取一条。管理端“套餐用户”同样以用户维度只展示结束时间最晚的一条当前套餐。

### 4.2 套餐额度不是自然日刷新

正常套餐额度当前以 `user_subscription.start_time` 为锚点，按北京时间 rolling 24 小时刷新：

- 第一个周期：`start_time` 到 `start_time + 24h`；
- 后续每 24 小时进入新周期；
- 最后一个周期不超过套餐 `end_time`。

赠送额度应复用这一语义，不能重新使用北京时间 0 点刷新，否则会重新引入日卡跨 0 点多拿一次额度的问题。

### 4.3 当前请求前准入

文本请求在模型解析、请求长度检查和价格预估后进入 `ProxyService._assert_text_request_allowed(...)`：

1. 刷新用户套餐缓存；
2. 有有效套餐时调用 `SubscriptionService.check_quota_before_request(...)`；
3. 套餐不足时尝试余额兜底；
4. 返回 `BillingAdmissionDecision`，低资产用户再经过 Redis 并发闸门。

当前 `check_quota_before_request(...)` 只判断 `remaining_amount > 0`，并未使用本次请求的预计消费来保证本次请求可被完整覆盖。

当前余额预检规则分两类：

- `billing_type=request` 等精确金额请求：余额必须覆盖预计金额；
- 普通 Token 请求：只要余额大于 0 即放行，即使 `estimated_total_cost` 高于余额也会继续。

### 4.4 当前请求后真实落账

文本和部分美元按次请求成功后统一进入：

- `ProxyService._finalize_successful_text_request(...)`
- `ProxyService._deduct_balance_and_log(...)`
- `ProxyService._deduct_balance_and_log_once(...)`

当前落账已支持同一请求拆分：

- `subscription`：全额由正常套餐承担；
- `mixed`：正常套餐先承担一部分，剩余金额扣余额；
- `balance`：全额扣余额。

正常套餐是 Token 口径时，系统按本次请求 Token 占比换算余额补差；成本口径时按美元占比换算。`ConsumptionRecord.quota_consumed_amount` 保存正常套餐实际承担的原生额度，`balance_before/balance_after` 保存余额变化。

### 4.5 当前并发保护只是限流，不是资产预占

`BillingConcurrencyService` 使用 Redis sorted set 为低资产用户限制并发，默认阈值 `$2`、默认并发数 `3`。它没有预占美元或套餐额度，因此多条请求仍可同时基于同一份剩余额度通过准入。

高于低资产阈值的用户通常不受该闸门限制。因此该能力只能降低穿透概率，不能证明“每个已放行请求都有可支付资产”。

### 4.6 模型解析与模型覆盖规则

用户请求模型先要求存在于启用的 `unified_model`，随后 `ModelService.resolve_model(...)` 可能通过覆盖规则重定向到另一个统一模型。最终定价、协议和渠道均使用解析后的 `UnifiedModel`。

因此“赠送额度模型”的判断必须基于**解析后的计费模型 ID**，不能只看客户端传入的字符串，也不能看渠道实际模型名；否则模型覆盖规则可造成错误命中或绕过。

### 4.7 图片积分与美元计费是两套资产

`billing_type=image_credit` 走 `UserImageBalance/ImageCreditService`，并不使用美元套餐或用户美元余额。赠送额度统一按美元，本期不把图片积分折算成美元，也不允许 `image_credit` 模型开启赠送额度标记。

`billing_type=free` 本身不产生费用，也无需占用赠送额度。

### 4.8 当前日志能力

`request_log` 和 `consumption_record` 可以展示正常套餐额度和余额，但无法表达“赠送 + 正常套餐 + 余额”三种来源，也无法表达多个重叠赠送批次分别消耗了多少。

此外，流式请求的后置记账异常当前会被捕获并仅写日志；部分日志读取又会把“上游成功但本地记账失败”的记录显示为成功。这会掩盖未落账事实，必须在本功能启用前一并收紧。

### 4.9 当前模型系列与套餐模板能力

`UnifiedModel.model_series` 已持久化 `gpt/claude/grok/gemini/other`，`ModelService.normalize_model_series()`、价格调整规则、模型管理页和用户模型列表均已复用该字段。因此系列套餐直接复用现有规范化系列编码，不另建系列主数据表，也不通过模型名称前缀临时推断计费资格。

当前 `SubscriptionPlan` 与 `UserSubscription` 只有一组 `plan_kind/quota_metric/quota_value`，`SubscriptionUsageCycle` 也只有每套餐每周期一份共享用量；套餐模板没有模型作用域。新增系列限制应保持这份共享额度结构，只增加模板系列关联和用户开通快照，避免选中两个系列后错误得到两份额度。

## 五、已确认的高风险点

### P0-1：现有代码允许普通 Token 请求把余额扣成负数

`apply_balance_charge(...)` 只有精确按次计费才检查 `balance >= amount`。普通 Token 请求只检查扣费前余额大于 0，随后直接执行 `balance - amount`。

结果是余额很少但请求很大时仍可先访问上游；并发请求还可能在前面请求扣完余额后才发生本地落账失败。

### P0-2：现有代码明确存在套餐越限分支

当正常套餐只剩少量额度、余额又不足时，当前逻辑会设置 `allow_quota_over_limit=True`，把本次完整用量继续写入套餐周期，余额不扣。这与本次强调禁止的行为直接冲突。

同一逻辑在套餐周期原子更新冲突后的重试分支中也存在，两个位置都必须移除，不能只修首个分支。

### P0-3：请求前无资产预占，并发请求可重复看到同一余额

Redis 的 3 并发限制不能阻止三条请求同时消费同一份低余额；资产较高时甚至没有该限制。只增加赠送周期的 `used_amount` 原子更新，仍会让后完成的流式请求在已把内容发给用户后才发现无法结算。

### P0-4：流式/WebSocket 内容可能先交付，落账失败后异常被吞

非流式路径大多在返回正文前完成落账；流式路径则在流结束后落账，异常通常被捕获并记录。没有预占时，无法保证已输出内容一定有对应资产。

### P0-5：现有三种 `billing_mode` 不足以审计新优先级

简单增加 `billing_mode=gift` 无法区分：

- 仅赠送；
- 赠送 + 正常套餐；
- 赠送 + 余额；
- 赠送 + 正常套餐 + 余额；
- 多个赠送批次共同承担。

必须保存请求级分摊明细，不能只留一个汇总字符串。

### P1-1：当前预估费用不是严格上界

普通 Token 请求未指定输出上限时，当前预估可能只包含输入；当前预估也没有完整覆盖缓存创建/读取的最坏组合。仅把 `estimated_total_cost` 改成硬拦截，会在部分场景误拦截，在另一些场景仍可能低估。

### P1-2：关键历史计费回归测试已不在当前测试集

历史文档中曾使用 `backend/app/test/test_subscription_compatibility.py` 覆盖大量套餐/余额边界，但当前仓库已删除该测试目录。现有测试只零散覆盖比例 helper 和套餐周期，不足以保护三段计费改造。

## 七、业务规则定稿

### 7.1 当前套餐、绑定套餐与有效期

1. 所有新计费资格统一采用半开区间：start_time <= now < end_time。
2. 实施时同步将 resolve_active_subscription() 的 end_time >= now 收紧为 end_time > now。数据库字段含义仍是“到期时刻”，展示值不变；只修正在精确到期时刻仍被认定有效的微秒边界。
3. 创建赠送事务取得 SysUser 行锁后，以同一个 now 再次调用 resolve_active_subscription()。
4. 请求中的 source_subscription_id 必须等于该方法本次选出的真实计费套餐 ID。仅满足“属于该用户且有效”的另一条重叠套餐不具备绑定资格。
5. start_time 使用创建事务内的统一业务时间，且强制 end_time > start_time。
6. 固定天数：end_time = start_time + duration_days × 24h，duration_days 为正整数，结果不得越过源套餐 end_time；越界返回业务校验错误，不做静默截断。
7. 跟随到期：end_time 直接保存创建时源套餐 end_time 快照。
8. 套餐续费生成新 UserSubscription 时，旧赠送不延长、不换绑；管理员可针对新的当前套餐再发新批次。
9. 多套餐重叠仍沿用 end_time DESC、id DESC 选出唯一当前套餐；只有该套餐可接受本次赠送。
10. 源套餐取消、被新套餐覆盖或状态失效后，绑定赠送停止接受新预占；已提交的在途 reservation 按快照结算。
11. “被新套餐覆盖”仅指 `activation_mode=override` 将源套餐改为 cancelled；`append` 创建未来套餐不影响当前源套餐及其赠送。
12. 所有可以开通或覆盖套餐的入口统一调用加锁后的 `SubscriptionService.activate_subscription/activate_plan_subscription`：管理端、支付回调与代理发放不得各自绕过用户锁。

### 7.2 赠送周期与多批次

1. daily_quota_usd 使用 DECIMAL(20,6)，资产运算全程使用 Decimal。
2. 周期锚点为赠送 start_time，按北京时间 rolling 24h，末周期截断于 end_time。
3. 周期唯一键为 bonus_grant_id + cycle_index，不以自然日期作为唯一性。
4. 同一用户允许多个重叠有效批次，额度叠加；分配顺序为 end_time 升序、grant_id 升序。
5. 页面同时展示 quota、used、reserved、available 和 next_reset_at。
6. 到期、取消和创建操作均取得同一用户锁；取消只阻止新的 reservation，既有 allocation 仍按其 source_id 结算。
7. 重复取消为幂等成功；取消时间、操作者、原因写入审计字段。

### 7.3 模型资格与并发修改语义

1. unified_model.bonus_quota_enabled=1 表示 token/request 美元计费可使用赠送额度。
2. image_credit 和 free 保存 bonus_quota_enabled=1 时，由后端抛出 ServiceException。
3. 命中对象是 ModelService.resolve_model() 返回的最终 UnifiedModel，不使用客户端原始模型名，也不使用渠道 actual_model。
4. unified_model 增加 billing_config_version。模型计费字段或赠送开关每次更新时原子加一。
5. 候选报价保存模型版本；reserve 在用户锁内复读该版本。版本不一致时，本次不改资产，回到候选准备阶段重建一次；再次冲突则返回可重试错误。
6. reservation 提交是赠送资格的线性化点。提交前的模型开关变更按新值，提交后的变更不影响在途结算。
7. subscription_bonus_enabled=0 时禁止创建新赠送、禁止新请求分配 bonus；已有 reservation 的 settle/release/reconcile 始终继续。

### 7.4 套餐模型系列作用域

1. 套餐模板新增 `model_scope=all_models/selected_series`：
   - `all_models`：兼容现有模板，对所有最终解析模型生效；
   - `selected_series`：只对关联表中选中的一个或多个系列生效。
2. 系列编码只允许复用 `ModelService.normalize_model_series()` 的 `gpt/claude/grok/gemini/other`；请求体不接受 `all`、空字符串或名称前缀。管理员选择“指定系列”时至少选择一项，重复项规范化后拒绝保存。
3. `plan_kind` 继续表示整份套餐池是 `daily_quota` 或 `unlimited`，`quota_metric/quota_value` 继续只保存一份。选择多个系列时共享同一个 `SubscriptionUsageCycle`，例如 GPT+Grok `$100/天` 是合计 `$100/天`，不是每系列各 `$100/天`。
4. `daily_quota` 继续兼容 `total_tokens/cost_usd`，管理端默认展示美元并允许选择现有两种口径；`unlimited` 沿用当前系统的内部硬上限策略，不因系列限制另复制额度。
5. 开通模板套餐时，在同一事务把 `model_scope` 和规范化系列集合复制到 `UserSubscription` 及 `user_subscription_model_series`。模板后续编辑、停用或删除系列关联均不影响已开通套餐。
6. 历史模板和历史用户套餐在没有显式作用域快照时按 `all_models` 解释，迁移不得把它们误改成“不覆盖任何模型”。
7. 系列资格以 `ModelService.resolve_model()` 返回的最终 `UnifiedModel.model_series` 为准。模型 override 后从 GPT 转到 Grok，则按 Grok 判断；渠道 `actual_model_name` 不参与。
8. 模型系列或影响计费的字段变更必须递增 `billing_config_version`。reserve 在用户锁内复核最终模型 ID、系列和版本，冲突时放弃本轮报价并重建，禁止以旧系列冻结资产。
9. 未命中套餐系列时，不创建正常套餐 allocation，也不增加 `SubscriptionUsageCycle.used_amount/reserved_amount`；请求仍可使用适用的赠送额度和余额。
10. 模型系列作用域只限制正常套餐，不限制赠送批次。赠送资格仍由最终模型的 `bonus_quota_enabled` 独立决定。

### 7.5 计费优先级

**最终解析模型同时命中赠送资格和正常套餐系列：**

赠送批次（最早到期优先） > 当前正常套餐 > 用户美元余额。

**只命中赠送资格、未命中正常套餐系列：**

赠送批次（最早到期优先） > 用户美元余额。

**未命中赠送资格、命中正常套餐系列：**

当前正常套餐 > 用户美元余额。

**两者均未命中：**

只使用用户美元余额；余额不能完整覆盖严格报价时，在 dispatch 前失败。

**免费模型：**

费用为 0，写请求日志，不创建正数 allocation。

**图片积分模型：**

保持 UserImageBalance/ImageCreditService 链路，与本次美元赠送及 reservation 隔离。

优先级描述的是实际结算顺序。为保证任意合法 usage 均有资产覆盖，预占可采用章节 8.4 的分量上界；结算后释放所有未使用冻结。

### 7.6 幂等与重复请求

1. 创建赠送使用 grant_request_id 唯一键，并保存 normalized_payload_hash。
2. 相同 grant_request_id 且规范化 payload 一致时返回原记录；内容不同返回 IDEMPOTENCY_CONFLICT。
3. 每个逻辑计费请求使用唯一 request_id；故障转移复用原 request_id，不按渠道新建 reservation。预占的 quote_payload_hash/candidate_set_hash 必须同时匹配，否则返回幂等冲突并停止 dispatch。
4. Responses WebSocket 的每个 turn 生成独立 request_id；连接本身不共享 reservation。
5. settle、release、人工处理和视频终态回调均带 operation_id，并通过唯一事件键加 version CAS 保证重复调用只返回既有结果。

## 八、严格报价、冻结快照与分摊公式

### 8.1 选择的候选策略

本方案选用“全部本地候选准备完成后，一次性按最坏候选预占”，不采用先低额预占再边 dispatch 扩容：

1. 完成鉴权、模型解析、安全检测、上下文限制、请求字段合法性等纯本地检查。
2. 查询、排序和过滤全部候选渠道。
3. 对每个候选执行协议映射、模型名替换、tool/system/instructions 转换、默认输出上限注入及渠道专属长度校验，生成不可变 PreparedBillingCandidate。
4. 对每个候选计算 QuoteEnvelope，最终 reservation 取各计费维度的分量上界。
5. 取得 Redis 并发 lease。该 lease 仍只做流量保护，不参与资金正确性。
6. 在 MySQL 短事务中 reserve。
7. reserve 提交后才允许创建 attempt 并进入首次网络 dispatch。
8. reserve 提交后到 `mark_dispatching()` 前的本地退出点只允许为：Redis lease 失效、客户端已取消、payload 不可变断言失败或内部异常；这些路径必须在确认无 attempt 后写 `release_pending` 并幂等释放。
9. 无渠道、渠道过滤失败、协议转换/长度校验失败、缓存 key 构建失败都发生在 reserve 前，因而不会留下真实冻结。

PreparedBillingCandidate 至少包含：channel_id、channel_name、upstream_api、actual_model、payload_hash、转换后 payload、输出上限、计数器上界、计费模型版本和报价版本。所有候选按固定排序序列化并计算 `candidate_set_hash`；该 hash 与 quote_payload_hash 一起进行 request_id 幂等校验。dispatch 必须使用该不可变 payload；如后续逻辑还会修改影响计费的字段，视为实现错误并在调用上游前终止及释放。

### 8.2 计数器上界

报价版本固定为 billing_quote_v2。定义：

- Uin：转换后 payload 的输入 Token 上界；
- Uout：发送给上游的输出 Token 上限；
- Uread：缓存读取 Token 上界；
- Ucreate：缓存创建 Token 上界；
- Uquota_token：正常 Token 套餐使用的原生 Token 上界；
- q6(x)：ROUND_HALF_UP 到 0.000001；
- ceil6(x)：向正无穷量化到 0.000001；
- bill_token(x, Mt)：对非负 x 执行 floor(x × Mt)，保持当前 token_multiplier 的正数截断语义。

所有函数必须接收 Decimal：`q6(x)=x.quantize(Decimal("0.000001"), rounding=ROUND_HALF_UP)`，`ceil6(x)=x.quantize(Decimal("0.000001"), rounding=ROUND_CEILING)`，`bill_token(x,Mt)=int((x*Mt).to_integral_value(rounding=ROUND_FLOOR))`；输入为负数、NaN 或 Infinity 直接报错，不转 float。分量计费在未量化的 Decimal 精度下相加，只在 `Cpay_actual` 统一 q6；预占只在 `Cpay_upper` 统一 ceil6，并由最后一个 allocation 承接尾差。

**输入上界：**

1. OpenAI Chat：对转换后的 messages、tools、tool_choice、response_format、metadata 及协议 framing 计数。
2. Anthropic Messages：对 messages、system、tools、tool_choice、thinking、context_management、betas 及 framing 计数。
3. Responses：对 input、instructions、tools、reasoning、text、include、metadata 及 item framing 计数。
4. 支持本地精确 tokenizer 的模型使用适配器精确计数；无 tokenizer 时使用 canonical JSON UTF-8 byte length + 明确的每 item/tool framing 上界，禁止继续沿用 len/2.5 作为 enforce 依据。
   - 无 tokenizer 的可执行定义为：`B = len(canonical_json(payload).encode("utf-8"))`，`F = 渠道适配器声明的 framing 字节上界`，`Uin = B + F`。由于每个输入 token 至少消耗1 个 UTF-8 byte，该值是保守上界；该适配器必须固定 canonical 排序、忽略字段和 framing 表，不得在请求中使用另一套计数。
5. 图片、文件或其他多模态输入必须由渠道适配器返回基于 detail、尺寸、页数和数量的 provider-specific 上界。元数据不足或计费规则未知时，enforce 模式在 dispatch 前返回 QUOTE_UNBOUNDED；shadow 仅记录原因。
6. 候选协议转换后的计数才有效；客户端原 payload 的估算只用于早期长度提示。

**输出上界：**

- OpenAI：优先 max_completion_tokens，其次 max_tokens；均缺失时向实际 candidate payload 注入 billing_default_output_token_limit。
- Anthropic：使用实际发送的 max_tokens；若 thinking budget 在目标协议中独立计费，candidate adapter 返回 max_tokens + thinking_budget，否则使用 max(max_tokens, thinking_budget)。缺失时注入默认值。
- Responses：使用 max_output_tokens；缺失时写回实际 candidate payload。
- 协议桥接以转换后的目标字段为准，同一数字既用于报价也用于上游请求。
- 配置合法范围预定为 1..32768，默认 4096；超过模型/渠道上限时先裁剪或报参数错误，再报价。

**缓存计数：**

当前结算将基础输入、cache-read、cache-create 分别相加，因此 v2 初始报价采用 additive 模式：

- Uread = Uin；
- Ucreate = Uin；
- Uquota_token = Uin + Uout + Uread，继续兼容现有套餐 raw_total_tokens 不含 cache-create 的规则。

若后续某适配器能证明三类计数互斥，可在新 quote_version 中使用 partitioned 模式；旧 reservation 始终按其 snapshot_version 结算。

### 8.3 美元费用公式

冻结以下非负 Decimal：

- Pin、Pout、Pread、Pcreate：四类每百万 Token 单价；
- Preq：按请求单价；
- Mt：token_multiplier；
- Mg：全局 price_multiplier；
- Ma：用户/分类调价倍率；
- Mf：Fast 倍率；
- Mc：长上下文倍率；
- Tlong：长上下文阈值。

长上下文计数兼容现逻辑：

Tcontext = input + output + cache_read。

候选上界满足 Uin + Uout + Uread > Tlong 时，Mc_upper 取配置的较高倍率，否则取 1。实际 Mc 由持久化 usage 和同一阈值快照计算。

Token 计费候选原始上界：

Craw_upper =
  [bill_token(Uin,Mt) × Pin
  + bill_token(Uout,Mt) × Pout
  + bill_token(Uread,Mt) × Pread
  + bill_token(Ucreate,Mt) × Pcreate] / 1,000,000。

用户美元预占上界：

Cpay_upper = ceil6(Craw_upper × Mg × Ma × Mf × Mc_upper)。

实际美元结算：

Cpay_actual = q6(Craw_actual × Mg × Ma × Mf × Mc_actual)。

由于所有 usage 分量均不超过对应上界，倍率与价格已冻结，且预占向上量化，应满足 Cpay_actual <= Cpay_upper。

按请求计费：

Cpay_upper = ceil6(Preq × Mg × Ma × Mf × Mc_upper)。

按请求成功时按相同快照 q6 结算；明确失败时为 0 并释放。free 为 0。image_credit 不进入本公式。

正常成本套餐若使用官方成本，冻结并计算：

Cofficial_upper =
  ceil6([Uin × Pin + Uout × Pout + Uread × Pread + Ucreate × Pcreate]
  / 1,000,000 × Mf × Mc_upper)。

它不乘 Mt、Mg、Ma，与当前官方额度口径保持一致。使用用户真实成本的套餐则 quota upper 等于 Cpay_upper。

### 8.4 三来源预占上界与实际结算

为了同时保证“按优先级结算”和“实际来源消耗不超过冻结”，报价器输出资产分量 envelope，而非只输出一个 estimated_total_cost。

1. 赠送：
   - G = min(全部有效赠送可用美元之和, Cpay_upper)；
   - 按 end_time、grant_id 将 G 拆到具体赠送周期。
2. 正常成本套餐：
   - 仅当 `normal_subscription_applicable=true`（all_models 或最终系列命中实例快照）时计算 Dq/P；否则 Dq=P=0。
   - Dq 为该套餐对整单的 quota upper；
   - P = min(套餐可用 quota, Dq)；
   - 先冻结 P，结算时只使用赠送未覆盖部分对应的实际 quota，剩余释放。
3. 正常 Token 套餐：
   - 仅当 `normal_subscription_applicable=true` 时计算 Dq/P；系列未命中时不创建 subscription allocation。
   - Dq = Uquota_token；
   - P = min(套餐可用 Token, Dq)；
   - 只要 G < Cpay_upper 就冻结 P；实际按赠送覆盖后的剩余美元比例计算套餐 Token，向上量化但上限为实际 raw quota Token。
4. 余额：
   - 对成本套餐，计算 rho_max：每个会消耗 quota 的计费分量中“用户美元单位成本 / 套餐 quota 单位成本”的最大冻结比值；quota 单位成本为 0 的分量进入 Czero_upper；
   - 对 Token 套餐，rho_max 为四类中每原生 quota Token 的最大用户美元单价，cache-create 因不计入当前 Token quota 而进入 Czero_upper；
   - 安全上界：
     Buncovered = Czero_upper + max(Dq - P, 0) × rho_max；
     B = ceil6(min(max(Cpay_upper - G, 0), Buncovered))；
   - 当成本套餐 quota 与用户美元同口径时，rho_max=1、Czero_upper=0，公式退化为精确的“赠送后套餐、不足进余额”。
5. 预占成功要求每个具体 bonus cycle、subscription cycle 和 UserBalance 都覆盖其 envelope 分量。Token 套餐混合价格下该 envelope 可能高于最终消耗，这是有意的 fail-closed 保守量；settle 后即时释放差额。
   - 成本套餐的 `Dq` 必须根据 quota metric 固定：`use_official_cost=1` 时为 `Cofficial_upper`，`use_official_cost=0` 时为 `Cpay_upper`；Token 套餐的 `Dq` 为 `Uquota_token`。它们不得在 settle 时重新读取当前套餐配置。
6. 实际结算调用同一个纯函数：
   - 先从已预占赠送批次扣 min(实际剩余美元, 该批次 reserved)；
   - 计算赠送后的剩余比例；
   - 正常套餐按 cost_usd 或 raw Token 口径消耗；
   - 最后余额承接剩余美元及 6 位量化尾差；
   - sum(settled_cost_usd) 必须精确等于 total_cost。
7. 性质测试针对合法 counter 空间随机及边界生成 usage，必须始终满足：
   - actual cost <= reserved cost；
   - 每个 source settled <= source reserved；
   - actual subscription quota <= reserved subscription quota；
   - sum allocations = actual cost；
   - used + reserved <= limit；
   - balance - reserved >= 0。
8. 任一适配器返回超出 snapshot 上界的 usage，先尝试同锁序补充冻结；补充失败进入 underfunded，不写穿任何资产。
9. `rho_max` 不能在实施中作为自由解释的参数；`BillingQuoteService.build_asset_envelope()` 必须按每个可计费分量生成单位成本候选集，显式排除不进入该 quota metric 的分量，再取 max；候选集为空时 `rho_max=0`，其费用全部进入 `Czero_upper`。
10. 正式实施前将 8.3/8.4 公式固化为带输入/输出类型的伪代码和 golden vectors；任一候选协议无法证明分量上界时，整个逻辑请求在 enforce 模式不 dispatch。

Token 套餐的实际分摊固定采用“美元比例映射回原生 Token”，不允许实现时自行选择舍入方向。令 `C` 为 q6 后实际总美元成本、`g=min(C,赠送实际承担)`、`r=0 if C=0 else (C-g)/C`；赠送按各费用分量占 `C` 的比例分摊，最后一个分量承接 6 位尾差。对进入 Token quota 的 input/output/cache-read 分量，将其原生 Token 乘 `r` 后求和并向上取整得 `Qneed`；cache-create 等不进入 Token quota 的费用保留为余额候选。`P=min(Qneed,已冻结套餐Token)`；若 `P=Qneed`，套餐承担全部剩余 quota-bearing 美元，否则按 `P/Qneed` 比例承担，最终余额精确承接非 quota 分量、未覆盖比例和 q6 尾差。套餐 Token 和套餐美元归因都不得超过各自 reservation allocation。

首批 golden vectors 至少固定：

| C / 原生 quota Token / 非 quota 成本 | gift | 可用套餐 Token | 期望 |
|---|---:|---:|---|
| `$10 / 100 / $0` | `$4` | `60` | gift `$4`、套餐 `60 Token/$6`、余额 `$0` |
| `$10 / 100 / $0` | `$4` | `30` | gift `$4`、套餐 `30 Token/$3`、余额 `$3` |
| `$10 / 100 / $2` | `$4` | `60` | gift `$4` 按分量比例分配、套餐 `60 Token/$4.8`、余额 `$1.2` |
| `$0.000001 / 1 / $0` | `$0` | `1` | allocation 合计严格 `$0.000001`，余额无负尾差 |

golden case 同时断言 `sum(settled_cost_usd)=C`、`P<=reserved_quota`、每来源 settled 不超过 reserved，并对所有费用分量顺序置换得到相同汇总结果。

### 8.5 可重启价格与主体快照

reservation 必须持久化 versioned JSON 及常用标量，不能在 settle 时依赖当前模型对象：

- 主体：user_id、agent_id、user_api_key_id；
- 模型：requested_model_id/name、resolved_model_id/name、resolved_model_series、billing_config_version、billing_type、bonus_quota_enabled；
- 套餐作用域：subscription_id、model_scope_snapshot、model_series_snapshot（稳定排序数组）、normal_subscription_applicable；
- 路由：候选摘要、稳定排序的 `candidate_set_hash`、最终 channel_id/name、actual_model、upstream_api、payload_hash；
- 单价：Pin、Pout、Pread、Pcreate、Preq；
- 倍率：Mt、Mg、Ma、adjustment source/rule id、Mf、Mc、Tlong、service_tier；
- 报价：quote_version、counter_mode、四类 usage upper、quota upper、各候选 quote、量化模式；
- 实际 usage：原始四类 Token、billable 四类 Token、各成本分项、context tokens、usage 来源和捕获时间；
- 生命周期：attempt_no、dispatch/accepted/first_byte/terminal 时间、heartbeat、upstream_task_id、worker lease；
- 上游重试：每个 attempt 发送稳定 `upstream_idempotency_key`；仅在上一次有明确未接受/未计费证据时允许故障转移，不支持幂等键的渠道在 unknown 状态下不得发送下一次尝试；
- 主体展示快照：API Key 名称、模型名、渠道名，即使相关配置日后删除仍可审计。

quote_snapshot_json 与 usage_snapshot_json 均包含 schema_version。读取器至少兼容当前版本和前一版本；未知版本进入 manual_review，不使用当前价格猜算。

标量字段是状态查询、索引和管理端摘要的权威来源；versioned JSON 是报价/usage 重放计算的权威来源。创建或状态转移时必须由同一个不可变领域对象同时生成两者，并校验双方重复字段完全一致；写入前不一致整笔事务失败，读取发现不一致进入 manual_review 并告警，settle 不选择任一侧静默覆盖。

## 十、全局锁协议与事务边界

### 10.1 唯一资金锁顺序

所有会增加、减少、冻结或释放用户资金的路径遵循同一顺序：

1. 无锁只读 request_id 定位 user_id；不得在该查询上持有行锁跨越下一步。
2. SELECT SysUser ... FOR UPDATE，建立用户级线性化点。
3. SELECT billing_reservation ... FOR UPDATE；初次 reserve 则在用户锁内二次检查 request_id 后插入。
4. 锁赠送 grant/cycle，顺序固定为 end_time ASC、grant_id ASC、cycle_id ASC。
5. 锁本次 resolve_active_subscription() 选中的 UserSubscription，再锁其 SubscriptionUsageCycle。
6. 锁 UserBalance。
7. 锁 allocation/attempt/event。
8. 写 RequestLog、ConsumptionRecord、API Key 统计与操作审计。

任何路径都不得先持有资产行或 reservation 行再等待 SysUser。没有 reservation 的人工余额扣减仍按 SysUser → UserBalance。模型编辑不取得用户锁；reserve 通过 billing_config_version 乐观复核。

定位查询只读取 `billing_reservation.user_id` 标量，不触发 ORM relationship/lazy-load；SysUser 使用 tombstone 保留主键，因此定位后用户行始终可锁。所有资金事务使用显式列查询和显式 eager load，Session 在事务结束后立即关闭，禁止在持锁期间跨 Session 或经序列化器触发隐式 lazy-load。

### 10.2 reserve 事务

1. 用户锁内检查 request_id：
   - 已有且 quote_payload_hash 与 candidate_set_hash 均相同，返回原状态；
   - 已有且任一 hash 不同，返回幂等冲突。
2. 复核用户未被删除/停用、计费模式、当前套餐、赠送资格、模型版本和 feature mode。
3. 创建 reservation 头，status=reserved、holds_assets=1。
4. 按固定顺序获取/创建周期并执行条件 UPDATE：
   - used + reserved + delta <= limit；
   - balance - reserved >= delta。
5. 插入 allocation。
6. 所有来源完整覆盖才提交；任一步失败整单回滚。
7. 资产不足返回 402，producer/network dispatch 调用次数必须为 0。

shadow 模式只写 status=shadow、holds_assets=0 的报价审计，不更新资产 reserved_amount，也不产生真实 allocation 冻结。

### 10.3 settle/release 事务

settle 或 release 先无锁取 user_id，再取得 SysUser 锁，随后按 10.1 重锁并校验 state_version：

- settle 的最终资产变化、RequestLog 主记录、ConsumptionRecord、API Key 统计、allocation 与 reservation=settled 在同一数据库事务；
- 任一日志写入失败则事务整体回滚，不会留下“资产已扣、主记录缺失”；
- release 同事务减少所有 reserved_amount、更新 allocation 和 reservation=released；
- 重复调用若已在目标终态，返回原结果；
- 允许前态或 version 不匹配时重新读状态，不盲目重复扣减。

### 10.4 死锁、锁等待与 worker claim

1. 数据库死锁或 lock wait timeout 最多重试 3 次，指数退避加随机抖动。
2. 每次重试均开启新 Session，并由 request_id/operation_id 幂等键重新读取状态。
3. 三次后写 failure_code=DB_CONTENTION，保留可恢复状态并告警。
4. 多实例 worker 的 claim 是一个独立短事务：仅以 FOR UPDATE SKIP LOCKED 选 reservation/event、写 worker_id 和 lease_until 后立即提交；该事务不触碰 SysUser 或资产。
5. claim 提交后，worker 再按 10.1 执行资金事务，因此不存在“持 reservation 等用户”的反向链。
6. worker 崩溃后 lease 到期可被其他实例重领；CAS 条件同时检查 state_version 和 lease owner。

### 10.5 赠送取消、套餐取消、人工扣款和用户删除

- create_grant：SysUser → 当前 UserSubscription → grant。
- cancel_grant：SysUser → grant/cycle；只关闭新资格，不减少在途 reserved。
- cancel_subscription/套餐覆盖：SysUser → UserSubscription → 相关 grant；新预占随后看见失效，在途按 allocation 快照完成。
- activate_subscription/activate_plan_subscription：无论由管理 API、`PaymentService._activate_subscription_order()` 还是 `AgentAssetService.grant_user_subscription()` 调用，都先取 SysUser；`override` 再锁当前 UserSubscription 和相关 grant，`append` 只创建未来套餐且不失效 grant。
- BalanceService.deduct、AgentAssetService.reclaim_user_balance 以及全局检索得到的所有“减少 UserBalance”路径：SysUser → UserBalance，扣后必须满足 balance >= reserved_amount。充值、兑换码和推广奖励等只增加路径不会破坏冻结，但为了与人工 fund-and-settle 建立一致的用户级线性化点，仍应统一采用 SysUser → UserBalance 锁序。
- AuthService.delete_user：
  1. 先锁 SysUser；
  2. 查询 holds_assets=1 且状态非 settled/released 的 reservation；
  3. 存在时抛出 ServiceException(409, USER_BILLING_IN_FLIGHT)；
  4. 不存在时将 active grant 幂等取消，并将用户改为不可登录的匿名 tombstone；
  5. reservation、allocation、attempt、event、ConsumptionRecord、RequestLog 及最小用户主体键保留，不级联删除；原有直接删除 SysUser/UserBalance/UserSubscription 的实现必须改造。
- 删除用户与 reserve/settle 的竞争由同一 SysUser 行决定先后，不存在检查后插入的新窗口。

## 十一、可恢复状态机与对账

### 11.1 状态定义

| 状态 | 是否持有资产 | 含义 |
|---|---:|---|
| shadow | 否 | 仅记录报价/实际差异，不冻结资产 |
| reserved | 是 | 预占已提交，尚无 dispatch 意图 |
| dispatching | 是 | dispatch 意图已持久化，网络结果可能未知 |
| dispatched | 是 | 上游已接受或已收到响应头/任务 ID |
| upstream_pending | 是 | 流或异步任务仍进行 |
| usage_captured | 是 | usage 已 durable 持久化，等待结算 |
| settling | 是 | worker 已领取结算 lease |
| settled | 否 | 已将 reserved 转为 used/balance deduction，终态 |
| release_pending | 是 | 已有可证明的零计费/未 dispatch 证据，等待释放 |
| released | 否 | 冻结已归还，终态 |
| underfunded | 是 | usage 超上界且补充资产失败 |
| manual_review | 是 | 上游是否计费或 usage 事实不确定，等待人工核查 |

settled/released 是资金终态。shadow 是非资金审计终态。underfunded/manual_review 继续冻结并阻断该用户新的付费请求。

字段映射固定如下：`billing_reservation.status` 保存上表的生命周期状态；`billing_reservation.accounting_status` 只保存对外投影（`not_applicable/pending/settled/underfunded/released/manual_review`），由状态转移事务同步更新。`request_log.status` 只表示上游/协议结果，不能承载 reservation 生命周期；`request_log.accounting_status` 和 `consumption_record.accounting_status` 从 reservation 投影，读取时以 reservation 为准并保留历史字段回退。任何代码不得用 `status=success` 推导账务已结算。

### 11.2 状态转移表

| 前态 | 事件/证据 | 后态 | 事务与幂等规则 |
|---|---|---|---|
| 无记录 | shadow quote | shadow | 独立插入，holds_assets=0 |
| 无记录 | reserve 成功 | reserved | 资产冻结与头/allocation 同事务 |
| reserved | 本地退出且尚未写 dispatch 意图，且同一事务确认不存在 attempt/dispatch intent | release_pending | version CAS；仅凭 expires_at 超时不得释放 |
| reserved | 即将执行首次网络调用 | dispatching | 先插 attempt，再提交，之后才触网 |
| dispatching | 收到响应头/上游 ID/明确 accepted | dispatched | attempt 与头 CAS |
| dispatched | 流或异步未终态 | upstream_pending | 保存 heartbeat/任务 ID |
| dispatching/dispatched/upstream_pending | usage 已确认 | usage_captured | usage snapshot + outbox 同事务 |
| usage_captured | worker claim | settling | lease owner + version CAS |
| settling | 资产及日志原子提交 | settled | 唯一 ConsumptionRecord 约束 |
| reserved/dispatching/dispatched | 明确未计费失败证据 | release_pending | 保存 evidence，不直接释放 |
| release_pending | release 事务成功 | released | 减 reserved 与终态同事务 |
| settling | usage 超 envelope 且补充失败 | underfunded | 保存 shortfall，资产不越限 |
| dispatching/upstream_pending | 状态长期未知 | manual_review | 保存全部 attempt 事实，继续冻结 |
| underfunded | 资产补足成功 | usage_captured | 先扩 reservation，再重试 settle |
| settling | worker lease 过期且无资产提交 | usage_captured | 新 worker CAS 重领 |
| manual_review | 管理员提交明确失败证据 | release_pending | operation_id 唯一、全量审计 |
| manual_review | 管理员补录 usage | usage_captured | 版本化 usage，不直接扣资产 |

### 11.3 崩溃窗口判定

1. reserve 提交后、dispatching 前崩溃：扫描只把 `expires_at < now` 当候选，不当释放证据。worker 取得用户锁和 reservation 锁后，必须在同一事务以 `status='reserved' AND state_version=:expected AND NOT EXISTS (SELECT 1 FROM billing_reservation_attempt WHERE reservation_id=:id)` 条件更新为 release_pending；同时要求 `dispatch_at/accepted_at/upstream_task_id/usage_snapshot_json` 均为空。任一条件不满足即保持冻结并重新分类，只有该条件更新影响 1 行才允许后续 release。
2. dispatching 提交后、网络调用前后崩溃：结果具有歧义，进入 manual_review，不按 TTL 释放。
3. 已 accepted/有 upstream task ID：进入 dispatched/upstream_pending，由轮询或对账获取终态。
4. usage_captured 后、settle 前崩溃：outbox 重放 settle。
5. settling 期间崩溃：资产、日志和 settled 在同一事务；未提交则 lease 到期回到 usage_captured，已提交则查询到 settled。
6. 日志插入失败：资金事务回滚，状态保持 usage_captured/可重试。
7. 异步任务长期 pending：刷新 heartbeat；超过业务 deadline 后进入 manual_review，expires_at 只触发扫描。

### 11.4 durable usage 与请求任务取消

1. usage 捕获调用独立 Session，将 usage_snapshot 和 usage_captured event 提交。
2. 同步请求优先在当前请求内 settle；同时 outbox 保证进程退出后仍可恢复。
3. asyncio.CancelledError、客户端断连、生成器 aclose 和应用 shutdown 分别显式捕获；清理逻辑使用受监督后台任务/asyncio.shield，但正确性最终依赖已提交 outbox，而非内存任务。
4. usage 尚未出现且 upstream 取消结果未知时，保存 attempt 与 manual_review；只有收到明确未接受/未计费证据才 release。
5. 应用停机先停止新 dispatch，再给 usage/outbox 提交和 settle worker 一个 drain 窗口；超时后的未终态由下一实例接管。

### 11.5 BillingReconciliationTask 多实例策略

1. backend/app/tasks/__init__.py 注册 billing_reconciliation_job；main.py 仅继续调用 start_scheduler()。
2. job 每次按索引批量 claim，例如 100 条，使用 SKIP LOCKED + lease。
3. 分别扫描：
   - reserved 且无 attempt；
   - dispatching/dispatched/upstream_pending 超 heartbeat；
   - usage_captured/settling；
   - release_pending；
   - underfunded/manual_review；
   - settled 但主日志/消费记录缺失；
   - 三类资产 reserved_amount 与活动 allocation 汇总不符。
4. 对明确状态执行幂等转移；不确定状态只告警和冻结。
5. max_instances=1 只保留为单进程降噪，跨实例唯一性由数据库 claim/lease 保证。
6. worker lease 超时可重领；测试覆盖两个 scheduler 同时运行和 worker 在处理中终止。
7. reservation 与 accounting event 分成两个 claim 队列和两个 lease namespace；event worker 只通过 reservation_id 触发 reservation CAS，不直接改资产，避免同一请求被两类 worker 交叉结算。

## 十二、六类请求调用时序

### 12.1 OpenAI Chat

目标入口：ProxyService.handle_openai_request()。

时序：

1. 鉴权、请求 ID、最终 UnifiedModel 解析。
2. 安全检测、上下文和字段校验；视频模型在此分流，不混入文本 reservation。
3. get_available_channels()、优先级与过滤。
4. 针对 openai、anthropic_messages、responses 三类目标预生成全部 PreparedBillingCandidate，完成桥接转换和输出上限注入。
5. BillingQuoteService.build_candidate_quotes() 并取 envelope。
6. BillingConcurrencyService.acquire_if_needed()。
7. BillingAllocationService.reserve()。
8. 每个候选调用前 mark_dispatching(attempt)，随后使用已冻结 payload 调用对应 stream/non-stream helper。
9. 候选只有出现明确未接受/未计费失败时才关闭 attempt 并继续后续候选；超时/断连等 unknown 先用 `upstream_idempotency_key` 查询上游，仍无法确定则停止故障转移并进入 manual_review。
10. 任一成功捕获 usage 并 settle；所有候选明确失败才 release；存在未知 attempt 则 manual_review。
11. finally 释放 Redis lease，它不改变资金状态。

### 12.2 Anthropic Messages

目标入口：ProxyService.handle_anthropic_request()。

顺序与 Chat 相同，候选准备额外覆盖：

- 原生 anthropic_messages；
- Anthropic → Responses 桥接；
- 兼容模式及 legacy tool guard；
- thinking budget 与 max_tokens 的目标协议语义；
- system、tools、cache control 转换后的计数。

_stream_anthropic_request() 和 _stream_anthropic_via_responses_request() 共用终态处理器，不在 helper 内各写一套扣费分支。

### 12.3 Responses HTTP

目标入口：handle_responses_request() 与 _prepare_responses_request_context()。

重构后 _prepare_responses_request_context() 只完成模型、候选、过滤与本地转换，不在渠道查询前 reserve。时序：

1. 图片工具请求先分流到现有图片积分/图片美元专用路径；本期赠送只处理 text token/request。
2. 校验 meaningful input、安全规则、高风险 tools、并行工具缓解。
3. 完整枚举并过滤 Responses 文本渠道。
4. 准备每个 mapped upstream target 的 payload。
5. 报价、lease、reserve。
6. _stream_responses_request() 或 _non_stream_responses_request() 执行。
7. usage durable 后 settle；所有候选失败时按 attempt 证据 release/manual_review。

### 12.4 Responses WebSocket

目标入口：handle_responses_websocket() 和 _forward_responses_websocket_turn()。

1. 握手只验证连接身份，不预占整个连接。
2. 每个客户端 turn 规范化后生成独立 request_id。
3. 每 turn 重新解析最终模型、候选渠道、转换 payload 和 quote。
4. 每 turn 独立 lease、reserve、attempt、usage、settle/release。
5. 前一 turn 的 reservation 达到资金终态或已 durable 进入待处理状态后，才接受同连接下一付费 turn，避免同连接绕过可用资产。
6. 客户端关闭连接时逐个处理活动 turn；未知上游状态进入 manual_review。
7. 上游 WebSocket 重连/候选切换仅新增 attempt。

### 12.5 缓存命中

涉及 CacheMiddleware.wrap_request() 与 StreamCacheMiddleware.wrap_stream_request()。

1. cache key、最终 resolved model、全部 PreparedBillingCandidate 和 canonical payload hash 必须在报价前确定；缓存命中也复用相同 `candidate_set_hash/quote_payload_hash`，缓存正文不得在 reserve/settle 前返回客户端。
2. 为兼容命中失效或竞态，reservation 按该 candidate 的完整网络最坏 quote 冻结，而非按“预计会命中”的较小数值。
3. reserve 后执行缓存包装：
   - 命中：不进入网络 dispatch，attempt 记录 cache_hit；使用缓存持久化 usage 进入 usage_captured → settle，结算成功后返回正文/流终端；
   - 未命中：正常 mark_dispatching 后调用上游；
   - 缓存记录缺 usage：进入 manual_review 或按可证明的上界 usage 结算，不以 0 费用成功。
4. 缓存写入失败不回滚已完成的资金结算；缓存读取正文损坏且尚未向客户端输出时 release。
5. 新测试验证“命中也收费一次、重复读取各自独立收费、缓存异常不产生免费 success”。
6. 所有可能调用 producer 的缓存未命中/旁路分支，在触网前断言 reservation=`dispatching` 且存在当前 attempt；缓存 wrapper 不暴露可绕过该断言的原始 producer 调用。

### 12.6 异步美元按次视频

目标入口：

- handle_video_request()；
- handle_video_request_and_wait()；
- handle_video_retrieve()；
- handle_video_content()；
- 各渠道 create/retrieve/content helper。

唯一责任规则：

1. handle_video_request() 是唯一创建 reservation 的入口。按次价格和倍率报价后 reserve，dispatch create。
2. create 明确失败且 evidence mode 证明未收费则 release；拿到 video_id/upstream_task_id 后保存到 reservation、attempt 和 VideoTaskBillingSnapshot。`accepted_create` 立即进入 capture/settle，其他模式进入 upstream_pending。
3. handle_video_request_and_wait() 只调用 create 一次并轮询，不新增 reservation。
4. retrieve/content 通过 user_id + video_id 找到原 reservation，只观察任务并调用统一 finalize_video_task_billing()；不重新解析模型或价格。
5. finalize_video_task_billing() 是唯一资产终结方法，并按 reservation 冻结的 `video_billing_evidence_mode` 执行：
   - `completed_usage` 在 completed 时 settle；
   - `accepted_create` 在 create accepted 时 settle；
   - `external_reconcile` 等待 provider 对账证据后 settle/release；
   - failed 仅在该模式下有明确未收费证据时 release，pending/unknown 保持冻结。
6. 多个 retrieve、wait、content 或 worker 同时看到终态时，由 state_version CAS 和 ConsumptionRecord 唯一键保证只结算一次。
7. content 在输出视频字节前确保 fixed-price settlement 已完成。
8. 客户端从不 retrieve 时，对账 worker 依据 snapshot 路由主动轮询。
9. wait 超时只停止本次等待，不释放；稍后成功仍结算。
10. image_credit 视频保持原积分链路，不创建美元赠送 allocation。

## 十三、流式终态、异常与异步语义

### 13.1 终端事件顺序

三类协议统一为：

最后一个含 usage 的上游事件
→ normalize_usage()
→ 独立事务 persist usage_snapshot + outbox
→ 同步尝试 settle
→ settle 成功后输出客户端终端标记
→ 关闭生成器。

具体终端标记：

- OpenAI Chat：data: [DONE]；
- Anthropic Messages：message_stop；
- Responses：response.completed 及最终 [DONE]。

普通内容 chunk 可在 reservation 保证下先转发；代表完整成功的终端标记必须排在 durable usage 和 settle 之后。settle 暂时失败时输出协议错误/关闭流，RequestLog.status 反映协议结果，accounting_status 保持 pending/manual_review，不伪装为完整成功。

settle 未成功时的协议行为固定为：OpenAI SSE 发送一个标准 `data: {"error":...}` 后关闭且不发送 `[DONE]`；Anthropic 发送 `event: error` 后关闭且不发送 `message_stop`；Responses 发送 `response.failed` 后关闭且不发送 `response.completed/[DONE]`。错误码区分 `BILLING_SETTLEMENT_PENDING` 与 `BILLING_UNDERFUNDED`，不得包含内部快照。若尚未输出首个 chunk，HTTP 层分别返回 503/402；若已输出部分内容，保持已发送 HTTP 状态但协议终态为 error。两种情况均令 RequestLog.status=`error`，账务状态保留真实 pending/underfunded/manual_review，并阻断该用户后续付费请求直到恢复。

### 13.2 usage 缺失

1. 上游有正式 usage：保存原始字段和归一化字段。
2. 缓存命中：使用缓存项随正文保存的 usage。
3. 流自然结束但无 usage：
   - 若适配器具备可证明的本地上界回退，按 quote snapshot 的明确规则保存 estimated_final usage；
   - 其余进入 manual_review，保持冻结。
4. usage 来源写 usage_source=upstream/cache/conservative/manual，展示和告警可区分。
5. 禁止“无 usage → 0 美元 → success”。

### 13.3 CancelledError、断连与 aclose

- 显式捕获 asyncio.CancelledError，并在重新抛出前提交已知 attempt/usage 事实。
- 客户端断连后继续完成 durable usage/settlement；若上游可取消，记录取消是否被确认。
- 生成器 aclose 走同一 finalize hook，不只依赖 except Exception。
- 未确认上游零计费时，不释放 reservation。
- 已输出部分内容又 underfunded 时：关闭流、accounting_status=underfunded、触发 P0 告警，并阻断该用户后续付费请求直到处理。

### 13.4 非流式

非流式收到完整响应后先捕获 usage 并 settle，再向客户端返回成功正文。settle 暂时失败返回 503 + `BILLING_SETTLEMENT_PENDING`，资产不足返回 402 + `BILLING_UNDERFUNDED`；原成功正文不返回，持久化状态供重试或人工核查。

### 13.5 服务停机

1. readiness 先置为 false，停止新 dispatch。
2. 等待活动请求将 attempt/usage 写入数据库。
3. drain settlement/outbox worker。
4. 超时任务保留数据库 lease/状态，由新实例接管。
5. 进程内变量只做性能缓存，不作为恢复依据。

### 13.6 视频终态

视频不能统一假设 completed 才产生费用。每个渠道必须配置并冻结 `video_billing_evidence_mode`：

- `completed_usage`：provider 文档和响应确认 completed 才产生费用，completed 才 settle；
- `accepted_create`：create accepted 即产生固定费用，accepted 后立即 durable capture + settle，后续任务状态只影响结果日志；
- `external_reconcile`：本地任务状态不足以判断费用，accepted 后保持冻结，由 provider 查询或对账回调提供明确证据。

未配置或未知模式在 enforce 下返回 `VIDEO_BILLING_EVIDENCE_UNDEFINED` 且 dispatch=0。长期 pending 不能推断免费，明确 failed 也只有在对应模式证明未收费时才 release；所有轮询入口共享 12.6 的 finalizer。

## 十六、配置、迁移与版本门禁

### 16.1 配置键

三份初始化 SQL 和升级 SQL 增加：

| key | type | default | 合法值/范围 |
|---|---|---|---|
| billing_reservation_mode | string | off | off/shadow/enforce |
| subscription_bonus_enabled | boolean | false | true/false |
| billing_default_output_token_limit | integer | 4096 | 1..32768 |
| billing_reconciliation_batch_size | integer | 100 | 1..1000 |
| billing_reconciliation_lease_seconds | integer | 60 | 10..600 |
| billing_capability_required_version | integer | 2 | >=2 |

新增 BillingRuntimeConfig 读取和校验层；配置修改后清理本进程缓存或使用短 TTL。非法值启动及保存时均报 ServiceException。

### 16.2 三态语义

- off：不创建新真实 reservation；用于结构部署阶段。两处套餐越限和余额透支漏洞修复仍始终生效。
- shadow：记录 quote、实际 usage 与误差，不写 reserved_amount，不改变现有资产选择；status=shadow、holds_assets=0。
- enforce：所有支持的美元文本/按次视频请求必须先真实 reserve。
- 模式只影响新请求；已有 reservation 无条件继续 settle/release/reconcile。
- subscription_bonus_enabled=true 的前置条件是 reservation_mode=enforce、schema 断言通过、运行实例版本门禁通过。

### 16.3 shadow 数据隔离

shadow 记录没有真实 allocation 冻结，所有 asset reserved 聚合查询必须带 holds_assets=1。shadow 不进入超时释放扫描，也不阻断用户。它只用于比较 actual <= quote 和计算误差分布。

### 16.4 混合版本门禁

旧实例不认识 reserved_amount，因此 enforce 前必须：

1. 所有新实例上报 billing_capability_version=2 和 schema version；
2. 从负载均衡摘除全部旧实例；
3. 等待旧实例活动流、WebSocket turn 和异步 create 请求排空；
4. 运维清单与健康接口确认活动实例版本全部兼容；
5. 再把 billing_reservation_mode 从 shadow 切到 enforce；
6. 最后启用 subscription_bonus_enabled 和赠送模型。

回滚到旧后端也必须反向排空，不能在新旧混跑时只切数据库 flag。运行时 preflight 若发现 schema/config 版本不匹配，拒绝开启 bonus 管理入口并触发告警。

`billing_capability_version` 必须同时声明 `legacy_full_balance_guard=true` 与 `legacy_no_quota_overrun=true`。配置保存接口和每个实例的 enforce 启动 preflight 都硬校验这两个 capability，不满足时保持 off/shadow；不能只依赖发布步骤文字或人工确认。集成测试通过注入旧 capability 证明 enforce 与 bonus 均无法开启。

### 16.5 幂等升级脚本

backend/sql/upgrade_subscription_bonus_quota_20260903.sql 沿用仓库 information_schema + 存储过程模式，每个字段、索引、表和配置键独立检查。DDL 自动提交意味着脚本可能部分完成，因此：

- 每一步可单独重跑；
- 索引按名称和列顺序双重核验；
- 已有同名但结构不符时停止并输出结构差异；
- 不在 migration 中重置历史 balance/used；
- 三类 reserved_amount 加入时 NOT NULL DEFAULT 0，并断言存量全为 0；
- 任一步失败保持 mode=off、bonus=false。

建唯一索引前必须运行重复预检并输出冲突主键、分组键和数量到 migration audit 结果：历史表已有业务数据的唯一键若发现重复，脚本使用 `SIGNAL SQLSTATE '45000'` 中止，不自动删除、不自动合并，由人工依据 RequestLog/ConsumptionRecord 审计后生成独立修复 SQL；新加 nullable `billing_reservation_id` 不回填历史行，因此历史 NULL 不冲突。所有新生命周期字段使用 VARCHAR + 应用校验，不扩展既有 `request_log.status` ENUM；若存量 ENUM 定义与预期不一致同样中止并报告差异。

### 16.6 大表 DDL

对 request_log 和 consumption_record：

1. 预检 SELECT VERSION()、information_schema.tables 的 table_rows/data_length/index_length。
2. 确认生产 MySQL 支持的 ALGORITHM：
   - 可 instant 的 nullable column 优先 ALGORITHM=INSTANT；
   - 唯一索引单独窗口使用 ALGORITHM=INPLACE, LOCK=NONE；
   - 不支持时采用在线 schema 工具或维护窗口，不隐式退化为长时间 COPY。
3. 设置合理 lock_wait_timeout，DDL 获取元数据锁失败即退出，不持续阻塞业务。
4. 先加列、后上线写兼容代码、再独立建索引。
5. 记录每步开始/结束和恢复指令；中断后根据 information_schema 从下一缺失对象继续。
6. 上线前在生产同版本副本测量耗时、临时空间和复制延迟。

### 16.7 初始化结构一致性

需要对以下三份初始化结构做自动比对：

- backend/sql/init.sql；
- backend/sql/initData.sql；
- sql/initData.sql。

比对目标包括新表列、类型、default、nullability、唯一键、索引和配置值，不只比较表名。

### 16.8 迁移后断言

升级脚本附带只读 assertion SQL，至少验证：

- 所有新表存在且引擎为 InnoDB；
- status/version/金额列精度正确；
- subscription_plan/user_subscription 的 model_scope 默认值正确，模板系列/实例系列快照表唯一键与索引存在；
- 所有存量模板和实例为 all_models 且无孤儿系列关联；selected_series 均至少一项且系列编码合法；
- request_id、grant_request_id、reservation+sequence、consumption reservation 唯一键存在；
- 三类 reserved_amount 非 NULL 且存量为 0；
- request_log.status 仍为原 ENUM；
- accounting_status 为独立 VARCHAR；
- 配置键及默认值正确；
- 三份 init 生成的新库 schema 一致。

   - 排空 HTTP 流、WebSocket turn 和视频 create；

   - 验证无活动冻结；
   - 再启动旧版本，杜绝新旧计费代码混跑。
5. 前端可独立回滚，不影响后端已存在的 grant 和 reservation。

7. 大表索引若造成性能问题，可在确认无依赖后单独回退索引；数据列和账务记录不删。
8. underfunded/manual_review 在回滚期间保持冻结并由人工处置，不按 TTL 清零。

## 二十四、风险与决策说明

1. **严格预占可能提高高上限请求的拒绝率。** 采用缺省上限写回、shadow 误差观测和明确降低上限提示；资产正确性优先于先调用后追账。
2. **Token 套餐与多价格分量混合时 envelope 偏保守。** v2 使用 rho_max 证明上界，先确保零穿透；后续可在新 quote_version 中引入更紧的优化器。
3. **流式部分内容先于最终结算。** reservation 已覆盖上界，终端成功标记在 durable usage/settle 后；异常具备恢复记录和 P0 告警。
4. **dispatching 是天然歧义窗口。** 先写意图可区分“确定未触网”和“可能触网”，后者保持冻结而非猜测释放。
5. **多个赠送批次增加明细数量。** 最早到期排序和 allocation 唯一序号保证确定性；管理列表用批量聚合控制性能。
6. **大表增列/索引可能影响生产。** schema 与索引拆阶段，先在同版本副本演练，不接受隐式 COPY。
7. **旧新实例混跑会绕过冻结。** enforce 和 bonus 的版本门禁、摘流与排空属于上线硬条件。
8. **硬删除会破坏审计主体。** 用户锁和非终态门禁保护在途资产，账务快照永久保留。
9. **核心 ProxyService 已很大。** 报价和状态机进入独立 Service，Proxy 只编排，避免复制公式。
10. **模型系列可被管理员修改。** 资格以 reserve 前最终模型版本复核为线性化点，实例保存模板系列快照；在途请求不随模型或模板编辑漂移。
11. **多系列额度语义易被误解。** 本期明确多系列共享一份套餐周期额度；若未来需要“每系列独立额度”，另建系列周期池并单独评审，不复用当前关联表暗中改变语义。

## 二十五、完成定义（Definition of Done）

只有同时满足以下条件才算功能完成：

- 管理员可对真实当前套餐用户创建、查看、取消赠送；
- 固定天数、跟随到期、rolling 24h、重叠批次及套餐变更语义均按 7 章执行；
