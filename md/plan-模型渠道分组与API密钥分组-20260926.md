# 模型渠道分组与 API Key 分组实施方案

## 方案状态

- 版本：Plan v2
- 日期：2026-09-26
- 当前阶段：已实施并完成验证（Plan v2）
- 任务级别：大型任务

## 用户原始需求

当前系统通过统一模型和渠道映射将用户请求转发到上游渠道。同一模型系列可能同时接入不同价格、不同供应商的渠道，需要增加分组路由能力，并让 API Key 选择分组。

已确认的业务规则：

1. 分组按模型系列管理，例如 GPT 系列可以有“特惠”和“正价”，Claude 系列可以有其他分组。
2. `/admin/models` 中每个具体模型的渠道映射需要指定所属分组。同一个分组可以绑定多个渠道，组内继续使用现有 priority、健康状态、熔断和故障转移逻辑。
3. 一个系列存在多个分组时必须设置一个默认分组。旧 API Key 没有分组信息，按各模型系列的默认分组路由。
4. 新 API Key 支持两种模式：
   - 通用：所有系列按各自默认分组路由；
   - 专用：绑定一个“模型系列 + 分组”，只能调用该系列、该分组下存在有效映射的模型。
5. 用户可以创建 API Key 后修改其模式、系列和分组，修改立即影响后续请求。
6. 选定分组的渠道全部不可用时不跨组回退，返回“当前分组暂无可用渠道，请先切换其他分组”；分组被停用或删除时返回“当前分组暂不可用，请先切换其他分组”。
7. `/v1/models` 和 `/models` 对通用 Key 返回所有实际可用模型，对专用 Key 只返回其系列和分组下实际可用的模型。
8. 站内聊天固定使用通用/默认分组，不因用户最近创建专用 Key 而改变路由。
9. 分组倍率只作用于 Token 文本计费，图片、视频和其他计费类型沿用现有计费逻辑。
10. Token 文本最终倍率为：

    ```text
    分组倍率 ×（用户独立倍率或模型系列全局倍率）× Fast 倍率 × 长上下文倍率
    ```

    用户独立倍率命中时覆盖现有系列全局倍率；未命中时使用系列全局倍率。`system_config.price_multiplier` 保持兼容，部署值为 `1`，不改变上述业务公式。

11. `/admin/logs` 和 `/admin/agent-logs` 增加请求分组列，并保留请求当时的分组身份和倍率快照。

## 当前系统基础与约束

- 后端为 FastAPI + SQLAlchemy，模型、渠道映射和价格规则分别位于 `backend/app/models/`、`backend/app/services/` 和 `backend/app/api/`。
- `UnifiedModel.model_series` 已存在，可作为分组作用域；`ModelCategory` 继续只承担模型价格类别职责，不复用为渠道分组。
- 当前 `ModelChannelMapping` 的唯一关系是同一统一模型与同一渠道一条映射，需要扩展为同一模型、同一分组、同一渠道唯一。
- 当前 API Key 只有用户归属和密钥状态，没有路由策略字段；历史记录必须按通用模式兼容。
- 当前价格解析为“用户专属规则优先，否则使用全局模型规则”，该优先级保持不变；分组倍率作为独立乘数只接入 Token 计费链路。
- 普通代理、原生透传、Responses、WebSocket、图片和视频均存在独立入口，分组解析必须集中为共享路由上下文，不能只修改某一个协议处理器。
- 根目录 `sql/initData.sql` 是当前对外初始化入口，升级脚本和初始化脚本需保持部署路径一致；历史 `backend/sql/` 脚本继续同步维护。

## 技术方案设计

### 1. 分组数据模型

新增独立的 `model_group` 表，不复用 `ModelCategory`、`Channel` 或复制 `UnifiedModel`。

建议字段：

- `id`
- `model_series`：所属固定系列
- `code`：系列内稳定编码
- `name`：显示名称
- `multiplier`：Token 销售倍率，复用现有倍率精度和正数范围校验
- `enabled`
- `is_default`
- `sort_order`
- `description`
- `created_at`、`updated_at`

约束：

- `(model_series, code)` 唯一。
- 同一系列最多一个启用默认组；存在多个启用分组时必须有一个启用默认组。
- 分组停用或删除前校验是否为系列默认组、是否仍有模型映射或 API Key 引用。
- 分组名称允许修改，但历史日志使用名称快照；分组 ID 作为 Key 的稳定引用。

### 2. 模型渠道映射

扩展 `ModelChannelMapping`：

- 增加必填 `group_id`。
- 唯一约束调整为 `(unified_model_id, group_id, channel_id)`。
- 创建、更新、列表和模型详情接口返回分组 ID、分组名称、系列信息。
- 同一渠道可以为同一模型加入多个分组；每组内部仍按现有渠道 priority、健康和熔断状态排序。

旧映射迁移策略：

- 为已有模型系列创建同名默认组（或复用已有初始化默认组）。
- 将旧的无分组映射回填到其模型系列默认组。
- 不复制统一模型、不改变模型名称和现有上游实际模型名。
- 迁移完成后，所有启用模型都必须能通过默认组解析旧调用路径；无法归属的异常数据进入升级校验报告并阻止静默上线。

### 3. API Key 路由策略

扩展 `user_api_key`：

- `group_mode`：`unified` 或 `special`
- `group_model_series`：专用模式的模型系列，通用模式为空
- `group_id`：专用模式绑定的分组，通用模式为空

兼容规则：

- 历史记录字段为空时按 `unified` 解释，不需要用户重新生成 Key。
- 专用 Key 创建和更新时校验分组存在、启用且属于所选系列。
- 专用 Key 只能绑定一个系列和一个分组，不能保存跨系列组合。
- 分组停用后保留 Key 绑定关系，调用时明确返回分组不可用；管理员或用户切换后立即生效。

API：

- 扩展创建接口，支持通用/专用模式。
- 新增 Key 路由策略更新接口。
- 列表和详情返回可读的模式、系列、分组名称和状态。
- 新增分组选择 options 接口，返回各系列启用分组、默认组和可选模型系列，前端不自行推导。

### 4. 统一路由上下文

新增共享的路由解析能力，输入 API Key、请求模型和协议，输出：

- 请求模型和最终统一模型
- 适用的模型系列
- 当前 Key 模式
- 选定分组及其状态
- 当前分组允许的渠道映射

解析顺序：

1. 校验请求模型并保持现有模型改写/解析语义。
2. 普通代理按最终统一模型系列解析分组；原生透传保持现有原始模型候选语义，但必须经过同一 Key 分组限制。
3. 通用 Key 选择该系列默认组；专用 Key 要求请求系列与 Key 系列一致，并选择 Key 绑定组。
4. 只在已选分组内执行协议能力、映射启用、渠道启用、健康、熔断和 priority 过滤。
5. 无有效映射时返回分组专属错误，不跨组重试。

接入范围：

- OpenAI Chat Completions
- Anthropic Messages 和 `count_tokens`
- Responses HTTP 与 WebSocket
- 原生透传 HTTP/WebSocket
- 图片生成、编辑
- 视频创建、查询和内容接口

补充规则：

- 同一流式请求、WebSocket 会话和异步视频任务固定创建时解析出的分组；后续事件或查询不重新选择其他分组。
- 视频任务继续使用现有渠道快照和旧媒体计费逻辑，同时保存分组快照用于审计。
- 健康检查仍按后台渠道/映射执行，不带入用户 API Key 的分组策略。

### 5. 模型列表

- `/v1/models`、`/models` 使用已验证的 API Key 生成可用模型列表。
- 通用 Key：按每个系列默认组筛选，只返回至少存在启用映射的模型。
- 专用 Key：只返回绑定系列和绑定分组下存在启用映射的模型。
- 对应模型不可用时不返回其他分组的同名模型，避免列表与实际路由不一致。
- `/api/user/models`、`/api/user/chat/models` 保持站内聊天默认分组语义；如返回渠道/可用模型信息，统一复用默认组过滤逻辑。

### 6. Token 计费与快照

扩展文本计费上下文：

- 预检阶段先解析路由分组，再解析现有用户/全局价格规则。
- `group_multiplier` 只在 `billing_type=token` 的文本模型路径参与计算。
- 保持用户独立规则覆盖全局模型规则的既有优先级。
- `system_config.price_multiplier` 保留字段和兼容读取，部署值固定为 `1`，不额外改变本次业务公式。
- 最终文本倍率：`group × adjustment × fast × context`。

请求日志、消费记录和相关序列化增加：

- `group_id_snapshot`
- `group_name_snapshot`
- `group_multiplier_snapshot`
- 必要时增加独立的 `effective_text_multiplier_snapshot`，与既有系统/调整/Fast/上下文快照分开保存。

预检、成功扣费、失败日志必须复用同一份冻结计费上下文，避免管理员在请求过程中修改分组倍率导致前后不一致。

非 Token 计费：

- 图片积分、视频积分、按请求计费及其他类型不加入分组倍率。
- 现有用户/全局媒体价格规则和套餐官方额度逻辑保持不变。

### 7. 管理端与用户端

新增 `/admin/model-groups`：

- 按模型系列查看、创建、编辑、停用和设置默认分组。
- 展示分组倍率、映射模型数、引用 Key 数和启用状态。
- 默认组切换、停用和删除提供引用校验与明确错误提示。

扩展 `/admin/models`：

- 模型渠道映射新增分组选择。
- 映射列表显示分组、渠道、实际模型名、启用状态和优先级相关信息。
- 创建/编辑映射时只展示与模型系列一致的分组。

扩展 `/user/api-keys`：

- 创建弹窗提供“通用”和“专用”模式。
- 专用模式选择系列和分组。
- 表格展示当前模式、系列、分组和分组状态。
- 增加修改分组/切换通用模式操作。
- 创建和修改成功后刷新列表，旧 Key 不受影响。

扩展 `/admin/logs` 和 `/admin/agent-logs`：

- 增加请求分组列。
- 展示分组名称快照，必要时显示分组倍率快照。
- 保持原有日志筛选、详情和代理范围权限。

### 8. 数据库迁移和初始化

新增幂等升级脚本，例如：

- `backend/sql/upgrade_model_channel_group_20260926.sql`
- `sql/upgrade_model_channel_group_20260926.sql`

脚本职责：

1. 创建 `model_group` 表。
2. 为 `model_channel_mapping` 增加 `group_id`，调整索引/唯一约束。
3. 为 `user_api_key` 增加路由策略字段。
4. 为 `request_log`、`consumption_record` 和视频任务快照增加分组快照字段。
5. 初始化各已有模型系列默认组。
6. 回填历史模型渠道映射到所属系列默认组。
7. 对历史 API Key 保留空值并按通用模式解释。
8. 更新 `sql/initData.sql` 和 `backend/sql/initData.sql`，确保全新数据库直接具备完整结构。

迁移脚本必须支持重复执行检查，并在回填后校验：

- 每个启用模型系列存在启用默认组；
- 每条启用映射拥有有效分组；
- 同一模型、分组、渠道不存在重复映射；
- 历史 Key 可按通用模式解析。

## 主要风险与控制

1. **历史映射无法归组**：升级前检查所有启用模型系列并创建默认组；迁移后禁止存在无分组启用映射。
2. **某个协议漏掉分组过滤**：所有代理入口统一调用路由上下文，并为 Chat、Anthropic、Responses、WebSocket、图片、视频分别保留回归测试。
3. **预检和实际扣费倍率不一致**：在预检阶段冻结分组与倍率上下文，后续成功/失败路径只复用快照。
4. **专用 Key 越权调用其他系列**：在模型解析早期校验 Key 系列与最终模型系列，错误不进入渠道候选。
5. **分组停用后静默回退**：分组状态检查与候选过滤分离出明确错误码，禁止跨组候选合并。
6. **历史日志无法审计**：保存分组 ID、名称和倍率快照，不依赖当前分组表反查历史信息。
7. **站内聊天被新 Key 改变路由**：站内聊天继续使用通用/默认 Key 解析，补充自动 Key 选择回归测试。
8. **数据库唯一约束冲突**：迁移前清理重复映射，使用 `(unified_model_id, group_id, channel_id)` 作为新唯一键。

## 验收标准

- 历史通用 API Key 无需重新生成即可按系列默认组调用。
- 专用 API Key 只能访问绑定系列和分组的可用模型，修改后立即生效。
- 同一模型可在不同分组绑定不同渠道；同组多渠道仍可按现有策略故障转移。
- 选定分组无渠道时不会切换到其他分组，并返回明确错误提示。
- GPT/Claude 等系列的默认组、分组倍率和映射可在后台完成配置。
- 普通用户和有独立倍率用户的 Token 计费分别符合 `分组倍率 × 全局/用户倍率 × Fast × 长上下文`。
- 图片、视频和其他非 Token 计费行为与改造前一致。
- `/v1/models`、`/models` 返回与 API Key 实际可路由范围一致的模型。
- 管理端日志和代理日志能够显示本次请求实际使用的分组及历史快照。
- SQL 可重复执行，初始化数据库与升级后的数据库结构一致。
