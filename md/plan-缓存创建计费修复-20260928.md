## 任务分级与边界

按大型任务执行：涉及公共协议归一化、金额/套餐额度、总 Token、长上下文阈值、异常记账、流式/透传和回归验证。先评估方案并修订 v2，再实现。只修改本地仓库并提交 GitHub；不连接生产服务器进行变更，不部署、不重启、不改历史账单或模型价格。原有未提交改动必须完整保留，不混入本次提交。

## 技术方案

1. 复用 OpenAI Chat Completions / Responses 的共享解析能力：输入总量包含普通输入、缓存读取、缓存创建；以互斥桶输出 `input_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens`，保留输入总量 `logical_input_tokens`。Anthropic 独立字段口径沿用既有解析，不能再次从它的普通输入扣缓存。
2. 缓存创建兼容 input_tokens_details / prompt_tokens_details 中的 cache_write_tokens、cache_creation_tokens，以及顶层 cache_write_tokens、cache_creation_input_tokens、cache_write_input_tokens、cache_creation_tokens。读取兼容 cached_tokens 及已有顶层别名。按确定优先级选择单一值，不累加别名；明确的零覆盖后备字段；缺失/无效值安全回退，负值和超过总输入的缓存桶不得引入负数或放大总量。
3. 不以“缓存未命中”或 CPA 端口推断创建量；仅根据明确的上游字段分桶，避免旧逻辑把整段输入同时按普通输入和创建计费。标准 OpenAI 未返回创建字段时，仍按普通输入处理。
4. 入账金额分别使用现有普通输入、输出、缓存读取、缓存创建价格和倍率。不调整任何定价。总 Token / raw_total_tokens / API key 累计 / 套餐 Token 额度 / 长上下文计算包含四个互斥桶；统一计费成功与异常记账的总量口径。
5. 校验 Responses/Chat 同步与流式、UsageObserver 透传都复用共享解析。已有页面支持创建量展示，无需重新设计 UI；只对会重新计算并遗漏创建的输出修正。
6. 用三个真实数字组合、全缓存/零值/别名/异常值、CPA 无创建字段、标准 OpenAI、Anthropic 和隐藏 reasoning 回归验证。增加端到端本地入账测试核对费用、总量、配额和失败记账；不得依赖生产 API 或生成收费请求。

## 风险与防护

- 不同协议输入语义不同：仅对总输入口径拆分，不改变 Anthropic 解析。
- 同名别名和明确零值：确定优先级，避免重复计费或错误后备。
- 总量修复会影响长上下文门槛和 Token 套餐：专门验证包含创建且只计一次。
- 历史记录不能仅凭输入量恢复缓存创建：本任务不做推算补账。
- 工作区存在无关未提交修改：保存基线，选择性暂存本任务补丁，并在隔离的干净提交上复验后推送。

## Plan v2：核查补充与方法级 To-Do

- 历史兼容：不重算已存历史 RequestLog / ConsumptionRecord；尤其历史 CPA 的 creation 可能与 input 重叠，不直接在历史展示修复函数中增加 creation。新成功和新记账失败记录均存正确四桶总量；LogService 保持读取既有总量，不推算历史缺失桶。
- OpenAI 字段顺序：Responses 优先 input_tokens_details、然后 prompt_tokens_details，Chat 顺序相反。每个 details 内创建依次 cache_write_tokens、cache_creation_tokens、cache_creation_input_tokens、cache_write_input_tokens；最后顶层同义字段。读取 details.cached_tokens 优先，再顶层 cache_read_input_tokens / cache_read_tokens / cached_tokens。只取第一个有效非负整数，显式 0 为有效值。负数、布尔值、非整数、非数字不是可收费 token，忽略并继续查找后备；缓存量越界时读取优先裁剪至总输入，再把创建裁剪至剩余输入，并记录无正文、无凭据的数值告警。
- 输入总量必须由上游 input_tokens / prompt_tokens 提供，不用缓存字段倒推不存在的输入，不用 JSON 长度估算。输出继续保留已有 Chat reasoning/total 兼容，避免把缓存创建补成额外输出。
- 透传：UsageObserver 合并原始 usage 中实际出现的字段（嵌套 details 逐字段合并）；重新生成完整归一化快照，不逐字段 max；显式 0 和下降量覆盖，缺失字段保留。不改写透传响应字节。Anthropic 使用原有路径，本次补丁不得依赖工作区尚未提交的 Anthropic 改动。
- 总量：raw_total = raw_input + raw_output + raw_read + raw_creation；billable_total = 各桶分别乘 Token 倍率并沿用 int 取整后相加；context_tokens 沿用本系统含输出的口径，并加上创建，倍率判断基于原始四桶总量。
- 定价：只分类，不调整价格。示例若输入/输出/读取/创建单价仍为 20/100/2/25 每百万、有效倍率 3，则第一条归类后的费用为 15.996930（非声称上线后减少费用），历史实际扣款不修改。

## 方案评估意见处理

1. P1 流式快照：新增必改 UsageObserver OpenAI 原始 usage 合并方法；保留旧 _merge 供 HEAD 的 Anthropic 分支使用，不依赖未提交的 Anthropic 优化。ProxyService._collect_stream_billing_tokens 在存在 _upstream_cache_usage 的实际快照时，按 collected_usage 的显式值（含 0）/上游快照/回调值选择；无实际快照时保持已有非零回调优先。has_usage 用实际快照存在性或非零 usage，区别全零有效快照与初始化的两个零占位。
2. P1 历史：不更改 LogService._visible_token_totals，也不重算旧 CPA/Anthropic 历史行；只让新失败日志直接持久化正确四桶总量。新旧记录读取回归分别覆盖。
3. P1 语义：上文 v2 已给出字段顺序及边界；Responses 不新增 Chat reasoning 回退，Chat 差额以拆分前总输入为基准。三个样例输出分别为 6262 / 3716 / 2159，来自本轮已读取生产记录与用户截图，非推算，原始总量分别为 194520 / 196776 / 190777。
4. P1 独立提交：不修改 AnthropicPromptCacheService，不暂存原有的 Anthropic/错误处理改动。HEAD 的旧 Anthropic 零值/TTL 行为保持原样，测试验证独立字段不会被二次扣减和四桶入账，并在干净暂存快照复验。本次不宣称解决 Anthropic 既有零值问题。
5. P2 总量：沿用本方案四桶/倍率公式，成功配额和 API key 按既有原始/计费口径；失败日志仍使用原始 token、倍率快照 1，不扣钱，仅记录完整实际用量。
