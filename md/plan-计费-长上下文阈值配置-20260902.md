# 计费-长上下文阈值配置 Plan

## 用户原始需求

当前 `admin/models` 管理模型时只能设置“长上下文 256k 后 2 倍计费”开关，长上下文阈值固定，无法适配超过 200k 等不同阈值后才执行双倍计费的模型。需要支持按模型设置：

- 是否开启长上下文双倍计费；
- 超过多少 Token 视为长上下文；
- 计费时继续复用现有双倍计费逻辑，只调整阈值判断来源；
- 尽量缩小改动范围，避免影响套餐额度耗尽后的余额兜底、余额扣减和计费记账。

## 现状分析

- 管理端已有模型级开关 `long_context_billing_enabled`，但列表和表单固定展示 `256k x2`。
- 后端真实硬编码阈值为 `ProxyService._LONG_CONTEXT_TOKEN_THRESHOLD = 262144`；界面文案称为“256k”，并非十进制 `256000`。
- 请求前预检查 `_build_text_quota_precheck` 使用该常量计算倍率和阈值快照；按请求计费且输出上限未知时，也用 `常量 + 1` 构造保守的 2 倍预检查。
- 请求成功后的 `_deduct_balance_and_log_once` 使用同一常量判断实际倍率并写入 `context_token_threshold_snapshot`。
- 套餐额度消费、套餐不足后的余额补扣、纯余额扣费均消费上述计费结果；这些扣减分支无需调整。
- `request_log` 和 `consumption_record` 已有阈值及倍率快照字段，日志页面也按快照展示，因此无需新增日志字段或修改历史账单展示逻辑。

## 技术方案设计

### 数据模型

在 `unified_model` 新增：

```text
long_context_token_threshold INT NOT NULL DEFAULT 262144
```

- 默认 `262144`，精确保留现有线上判断边界，避免迁移后已有模型计费行为变化。
- 该字段只在长上下文开关开启时影响倍率；关闭时倍率仍为 1。
- 后端仅接受大于 0 的整数，避免 0、负数或非法值导致所有请求误触发双倍计费。

### 后端

- ORM、创建/更新/详情 Schema、模型 CRUD 增加字段。
- `ModelService` 统一规范化阈值；新建默认 262144，更新未传字段时保持原值。
- `ProxyService` 增加模型阈值解析 helper，非法/历史缺字段场景回退 262144。
- 请求前预检查与真实扣费均通过同一 helper 获取阈值：
  - 倍率规则仍为 `开关开启 && context_tokens > threshold ? 2 : 1`；
  - 不修改 2 倍倍率值、上下文 Token 口径、成本公式、套餐额度公式、余额扣减和事务记账；
  - 阈值快照改为记录模型当时的实际配置值；
  - 按请求计费的保守预检改为使用 `模型阈值 + 1`。

### 管理端

- 保留现有开关。
- 开关开启时显示 Token 阈值输入框，默认 262144，可设置如 200000。
- 列表和移动端由固定 `256k x2` 改为显示实际阈值，如 `> 200,000 x2`。
- 保存前校验阈值必须为正整数。

### 数据库兼容

- 新增幂等升级脚本，只添加模型阈值字段，不回写或修改开关值。
- 同步 `backend/sql/init.sql`、`backend/sql/initData.sql`、`sql/initData.sql`。
- 迁移默认值采用 262144，使现有已开启模型在升级前后行为一致。

## 风险控制

- **扣费链路风险**：不调整 `total_cost_decimal` 之后的套餐/余额分支，只改变已有上下文倍率 helper 的阈值参数。
- **预检与实扣不一致**：两处必须调用同一阈值 helper，并对按请求计费保守预检使用同一模型阈值。
- **迁移改变历史配置**：新增列默认 262144，不修改现有开关及模型价格。
- **非法阈值误扣费**：Schema 与 Service 双层校验；运行时仍对历史异常数据回退 262144。
- **边界语义**：保持原规则“严格大于阈值才 2 倍”，等于阈值仍为 1 倍。
